# 사내비 답변 가독성 지침 조사와 적용 제안

작성: 2026-10-15 / AI 조사·코드 검토. 아래는 구현 전 조사 원본이며 당시 상태는 제안·미적용·실모델 미실험이다. 이후 승인된 16회 실행과 채택 판단은 이 폴더의 README.md를 따른다. 48회 검증 제안은 채택하지 않았다.
기준 HEAD: 389e936. 작업 트리의 웹 리팩터링 변경은 별도로 존재하며 수정하지 않았다.

## 1. 결론

현재 답변의 문제는 사실 오류보다 정보 구조에 있다. 범위 소개, 여러 업무 예시, 실행 한계, 다음 질문이 한 문단에 함께 있다. 간결함은 글자 수만 줄이는 것이 아니라 사용자가 필요한 항목을 쉽게 찾게 하는 것을 포함해야 한다.

추천은 기존 v5 내용 판단을 유지하고, 별도의 짧은 ‘답변 구성’ 지침을 시험하는 것이다. 기본은 짧은 자연어 문단, 병렬 항목은 불릿, 실제 순서가 있는 절차만 번호 목록으로 만든다. 모든 응답에 제목·표·목록을 강제하지 않는다. 이 결론은 공개 문서와 현 코드에 근거한 설계 제안이며 Luna에서 개선 효과를 측정한 결과가 아니다.

## 3. 현재 코드 확인

- `generation/prompts.py`: 정중하고 간결한 존댓말과 JSON 계약은 있지만 문단·목록의 사용 조건은 없다.
- `generation/profiles.py`: 기본 `examples_answer_scope_v5`. 범위·근거·필수 안내·조회 한계·말투를 제어하지만 가독성 규칙은 별도로 없다. 기존 짧은 예시도 대부분 한 줄이라 다문단 응답의 본보기가 없다. 이것이 이번 응답을 유발했다는 인과관계는 실험 전이므로 확정하지 않는다.
- `generation/validation.py`: JSON 역직렬화 후 answer 앞뒤 공백만 제거한다. 본문 내부 줄바꿈 제거 로직은 없다.
- 커밋된 `web/features/question/answer-markdown.tsx`: react-markdown, remark-gfm, remark-breaks 사용. 문단·불릿·번호 목록 지원, raw HTML 무시.
- 현재 미커밋 작업 트리에서는 공통 `web/components/markdown-content.tsx`로 이동 중이며 `message-item.tsx`가 이를 호출한다. 역시 Markdown을 지원한다. CSS에는 문단과 목록 간격이 정의되어 있다.
- 코드상 표시 기능은 있으나 이번 작업에서 사용자의 실행 브라우저를 재현하거나 실제 서버 응답 원문을 수집하지 않았다. 복사해 준 답변의 정보 구조와 현재 코드를 검토했다.

따라서 우선 프롬프트에서 의미 단위 구성을 생성하도록 하는 것이 적절하다. CSS 자동 줄바꿈은 화면 폭에 따른 개행이며 의미별 문단 구분과 다르다. 문자열을 마침표마다 사후 분리하면 소수·URL·인용 등을 깨뜨리고 목록의 의미도 결정할 수 없어 권하지 않는다.

## 4. 제안 지침 — 아직 적용하지 않음

```text
답변 구성:
- 먼저 질문에 대한 핵심 답을 짧게 말하고, 설명의 주제가 바뀌면 빈 줄로 문단을 나누세요. 짧은 단일 답변은 한 문단으로 충분합니다.
- 여러 업무 분야·선택지·준비물을 나열할 때는 짧은 불릿 목록을 사용하세요. 실제로 순서가 있는 절차에만 번호 목록을 사용하세요.
- 각 항목의 조건·예외·기한은 해당 항목과 함께 적으세요. ‘또는’인 선택지를 모두 수행할 단계로 바꾸거나, 읽기 쉽게 줄인다는 이유로 필수 안내를 빼지 마세요.
- 도움 가능 범위를 물으면 지원 범위 소개, 대표 업무 목록, 직접 조회·실행의 한계 순으로 나누고 필요한 다음 질문 하나로 마무리하세요. 이 구성을 다른 질문에 일괄 적용하지 마세요.
- 짧은 답변에는 제목·표를 억지로 붙이지 마세요. 강조가 도움이 될 때만 핵심 표현에 굵게 표시하고, 장식용 이모지·중첩 목록은 기본적으로 사용하지 마세요.
- 기존 JSON 응답 형식은 유지하고, 문단과 목록은 answer 문자열 안에 표현하세요. JSON 문자열의 줄바꿈은 올바르게 이스케이프하고 응답 전체를 코드 블록으로 감싸지 마세요.
```

다른 말투·지원 범위 규칙을 중복 작성하지 않는다. 실제 적용한다면 v5를 그대로 보존하고 예를 들어 v6 후보로 분리한다. 공통 build_prompt에 합쳐 과거 프로필까지 바뀌게 하지 않는다. 모델 설정·추론·토큰 상한·출력 모드는 바꿀 필요가 없다.

모든 응답을 한 템플릿으로 강제하면 단답·거절·재질문이 불필요하게 길어진다. 제목이나 불릿 개수만 평가하면 빈 항목·중복·내용 누락을 보상할 수 있다. 업무별 정확성이 가독성보다 우선한다.

## 5. 사용자 예시 재구성

아래는 AI가 작성한 편집 예시이며 실모델 실행 결과가 아니다. 제공받은 답변의 범위만 재구성했다.

이음웍스의 사내 업무 정보·규정·절차와 업무 도구 사용법을 안내해 드릴 수 있습니다.

- 휴가·근태
- 출장·경비
- 계정·권한·보안
- 문서·회의
- 고객 문의·개발 절차

신청·변경·취소·승인이나 개인별 상태 조회를 직접 하지는 않습니다. 궁금한 업무를 말씀해 주세요.

업무 도구 안내도 회사 문서의 근거 범위로 한정된다는 내부 규칙은 유지한다. 모든 카테고리를 항상 열거할 필요는 없고 대표 예시는 질문과 실제 자료에 맞춰 선택한다. 짧은 부재 안내나 범위 밖 응답은 불릿 없이 한두 문장으로 둔다.

## 6. 검증 제안 — 미실행

1. 동일 snapshot·모델 설정에서 기존 v5와 가독성 후보만 비교한다.
2. 12문항 × 두 프로필 × 2회 = 최대48회. 사용자 승인 후 실행할 제안이며 이번 조사에서 비용을 발생시키지 않았다.
3. 문항 유형: 도움 범위 2, 단일 사실 1, 순차 절차 2, OR 선택·예외 2, 부분 답변 1, 범위 밖 1, 모호함 1, 긴급 사고 1, 실제 조회·안내 혼합 1.
4. 기존 필수 안내·근거·권한·형식 판정과 별도로 핵심 답 위치, 의미별 문단, 적절한 목록 선택, 과도한 서식·중복, 모바일 탐색성을 판정한다.
5. 사고 절차에서는 긴급 조치가 서론 뒤로 밀리지 않는지, 시간·조건·선택 관계가 보존되는지 확인한다. 같은 내용을 더 보기 좋게 만들었는지와 단순히 정보를 삭제했는지를 구분한다.
6. JSON 파싱 뒤 실제 개행이 생기는지, 불릿·번호·굵게가 표시되는지, 360px 모바일와 데스크톱에서 가로 넘침·불필요한 스크롤이 있는지 확인한다. 실제 화면 사용성은 사람 검토 전까지 AI 검토 결과로만 보고한다.
7. 기준 예시: JSON 실패·새 중대 사실 오류 0, 필수 안내 퇴행 0, 도움 범위 질문의 두 반복에서 소개/목록/한계 분리, 단답·거절에 불필요한 목록 없음. 이는 제안 기준이지 이미 달성한 결과가 아니다.

## 7. 작업 범위

공식 자료 조사와 현재 코드 읽기, 이 임시 보고서 작성만 수행했다. 런타임·프롬프트·웹·서비스 기본값·Notion은 변경하지 않았다. 유료 모델 호출·테스트·커밋·푸시는 하지 않았다. 기존 미커밋 웹 변경은 보존했다.
