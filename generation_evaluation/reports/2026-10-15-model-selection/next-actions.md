# 최종 평가 이후 개선 순서

아래는 **후속 제안**이다. 최종20문항 결과를 본 뒤 이번 고정 후보를 수정하거나 기본 설정을 승격한 기록이 아니다.

## 1. 출력 형식을 제공자 계약으로 강제

최종 GPT 응답 중 일반 문장으로 출력된 원문은 그대로 parse_error로 남았다. 프롬프트에는 JSON 지시가 있지만 대조 예시는 평문 답변 형태이고, 모든71문서 뒤에 질문이 놓인다. 예시 형식과 긴 입력이 영향을 주었을 가능성은 있지만, 최종 문항에서 baseline과 이를 각각 통제하지 않았으므로 원인을 확정할 수 없다.

다음 개발 실험은 `{"answer": string}`의 strict JSON Schema를 제공자에 전달하는 변경 하나부터 비교한다. 추가 필드를 금지하고 거절·잘림·빈 응답·전송 오류는 명시적 실패로 유지한다. 프롬프트 예시도 계약과 맞출 후보를 별도로 비교한다. 모델의 평문 응답을 사후에 감싸서 이번 형식 실패를 통과로 바꾸지 않는다. OpenAI의 [구조화 출력 안내](https://developers.openai.com/api/docs/guides/structured-outputs)는 스키마 강제와 거절·미완성 처리를 구분한다. 이번 실험에서는 효과를 측정하지 않았다.

형식이 고쳐져도 문서 근거·조건·권한 정확성이 보장되지 않는다. 형식 성공률과8개 의미/지침 차원은 계속 따로 보고한다.

## 2. 답변 근거의 완전성과 적용 범위를 함께 검증

이번 evidence_first는 ID·원문 정확성을 검증했지만 필요한 근거를 모두 찾는 능력까지 보장하지 않았다. 빈 추출은 필수 안내를 누락시켰고, 한 구간이 정확하더라도 다른 조항의 예외가 빠지면 결론이 틀릴 수 있다. 단순히 추출 한 단계를 더 넣는 방식은 이번 결과에서 채택하지 않는다.

후속 후보에서는 문항의 필수 주장별 근거 포함 여부, 행위 주체·업무 대상·시간 기준점·조건 연결을 검사해야 한다. 먼저 개발 세트에서 원문 인용 정확성과 필수 근거 회수율을 별도 측정한 후 최종 답변 품질을 본다. 인용이 유효한지와 결론이 유효한지를 같은 검사로 취급하지 않는다. 무근거 정책·개인 상태·처리 완료를 만들어내면 출력하지 않는 실패 정책도 검토한다.

## 3. 문서 증가에 대응하는 입력 계약

문서가 추가되면 기존20문항 점수나 현재98,304 문맥의 성공을 그대로 인정하지 않는다. 새 snapshot에 ID·개정·본문 hash를 고정하고 질문별 근거·충돌·유효기간을 다시 검토한다. 입력 토큰과 출력 예약량을 제공자 tokenizer 기준으로 점검하고 cold/warm 지연·메모리를 함께 재측정한다. 이번 비용 예약의 UTF-8 상계는 과금 한도 방어이며 정확한 문맥 적합성 검증을 대신하지 않는다.

전체 입력 한도를 넘기거나 지연이 커지면 문서 선택을 별도 단계로 평가한다. 질문의 근거뿐 아니라 예외·상위 정책까지 회수하는지 먼저 확인하고 선택기 실패와 생성기 실패를 나눈다. 검색기·벡터DB 도입은 이번 범위 밖이며 구현한 것으로 기록하지 않는다.

## 4. 새로운 선정 세트로 재검증

이번20문항은 실패 분석을 했으므로 이후에는 회귀 세트로 쓴다. 새 그룹의 미공개 선정 세트를 만들어 형식 개선 이후 두 반복 안정 통과18/20 이상·중대한 오류0을 다시 확인한다. 사용자/업무 담당자가 판정 경계를 검토한 뒤 서비스 연결을 논의한다. 지금의 잠정 권장은 다음 실험의 우선 모델이며 운영 승인과 구분한다.
