# 전체 문서 생성: 속도 병목과 답변 근거 검토

2026-10-15. 사용자가 실험 설정·실행·TPS 개선·답변 품질 분석·일지 작성을 AI에 위임했다. 독립 생성 모듈 단계이며 서버 연결·사람 승인·전체 모델 평가 완료를 뜻하지 않는다. 관련 없는 분류 작업의 변경은 보존한다.

## 바뀐 계기

문서 한 건 smoke를 반복하는 대신 실제 프로젝트 snapshot 71건과 SEARCH_KNOWLEDGE 문항을 연결했다. 이 라벨은 지식 안내가 필요한 질문이라는 의미이지, 현재 문서로 모든 세부 질문에 답할 수 있다는 뜻은 아니다.

40,960 문맥에서는 입력 약67k가 초과했다. 98,304로 확장하자 실행은 가능해졌지만 모델 파일 약2.5GB 외의 KV 캐시가 커져 CPU/GPU 혼합 처리가 발생했다. 실행 성공과 속도·품질을 각각 측정할 필요가 생겼다.

동시 작업이 있던 첫 실행은 중단·제외했다. 정리 후 첫5건은 모두 completed/stop이었으나 약26분이 걸렸다. 이후4건의 출력토큰/전체시간은 약1.15 TPS였다. 이 수치는 순수 생성 TPS가 아니다.

## 실험 근거와 비교 원칙

원자료: 로컬 `tmp/generation-first5-isolated-20261015-065710/` 및 `tmp/generation-tps-quality-20261015/`. 후자에 입력 식별, 실행 환경 manifest, 전체 응답/usage/timing, backend 로그, GPU 표본, 실험 코드, 주장별 검토와 공식 참고자료를 보존한다. tmp는 원격 게시물이 아니다.

- 모델: Qwen3 4B Instruct 2507 Q4_K_M, Ollama0.33.3, RTX5060 Laptop8GB.
- 새 속도 비교: 문서71건, RQ0007, 문맥98,304, 출력128, temperature0/seed42. F16/Q4 캐시별 첫 호출·동일 요청 반복. 서버 재시작은 OS 파일 캐시 초기화를 뜻하지 않는다.
- 순수 생성 TPS는 `eval_count / (eval_duration / 1e9)`. 요청 전체시간과 prefill/load를 별도로 보존한다. 출력128 실험의 잘림은 품질 성공으로 세지 않는다.
- 품질: 기존5건 주장별 검토와 새 운영 조건의5건, 두 문항의 전체/수동 관련문서 × 기존/강화 프롬프트 비교. 기존5건은 샘플링이 통제되지 않아 캐시 단독 품질 효과 비교가 아니다.
- num_batch128 요청은 설치 backend에서512로 실행되어 채택하지 않았다. 설정 전달과 실제 적용을 로그로 구분했다.

## 속도 실측 결과와 적용

동일 문서·질문·샘플링·출력128·FA on·fit256에서 측정했다. 두 호출 모두 출력 한도에 도달한 속도 실험이며 정답 검토에 사용하지 않는다.

| 조건 | F16 생성 TPS | Q4 생성 TPS | 생성 속도 배수 | F16 전체시간 | Q4 전체시간 |
|---|---:|---:|---:|---:|---:|
| 모델 재적재 후 첫 호출 | 1.30 | 18.57 | 14.3배 | 253.79초 | 87.46초 |
| 동일 요청 반복 | 1.21 | 18.52 | 15.3배 | 106.89초 | 7.15초 |

F16 캐시13,824MiB / GPU14/37층에서 Q4 캐시3,888MiB / GPU37/37층으로 바뀌었다. 입력 문서·모델 가중치·문맥98,304는 유지했다. Q4 첫 입력 처리만76.88초라 새 입력의 첫 응답 지연은 여전히 크다. 반복 요청7.15초는 동일 prompt의 prefix cache 재사용 조건이며 모든 질문에 일반화하지 않는다. 각 조건2회 소규모 비교로 p95나 동시처리 성능은 측정하지 않았다.

[scripts/serve_generation_ollama.sh](../../scripts/serve_generation_ollama.sh)는 별도 loopback11435 서버를 시작한다. 기본 시스템 서비스는 바꾸지 않았고 관리자 인증도 요구하지 않았다. 호출 프로세스에 OLLAMA_HOST를 지정하는 사용법은 [생성 모듈 안내](../../generation/README.md#로컬-gpu-실험-실행)에 있다. 운영 기본값의 일괄 변경이 아니라 검증한 로컬 실험 프로필이다.

## 품질에서 확인한 문제

| 질문 | 문제 | 개선해야 할 평가 기준 |
|---|---|---|
| 급여계좌 변경 | 없는 메뉴와 변경 조건을 덧붙임 | 전용 정책 부재를 밝히고 일반 문의 창구와 실제 변경 메뉴를 분리 |
| VPN 승인 확인 | 전용 기준이 없어 유보한 것은 적절 | 일반 IT 문의 연결 등 유용성은 따로 평가 |
| 거래처 계좌 정정 | 직접 변경 불가 설명 누락, People팀 연결 근거 부족 | 실행 한계 및 지급 담당 범위 유지 |
| 출장 영수증 분실 | 없는 필수사항·대체증빙·상태·문서 섹션을 생성 | 허구 세부사항과 같은 신청 건 보완 규칙 누락을 별도 검사 |
| 보안 신고 진행 | 15분 인수 목표를 보장으로 변형 | 조건·책임 주체·기록 의무와 조회 가능성 구분 |

보안 > 사고 신고 메뉴는 069/071에 존재한다. 이를 환각으로 잘못 세지 않는다. '승인 완료'도 일반 표현으로 문서에 있지만 UI 상태명 보장과 구별한다. 검토는 실제 문서 전체를 확인해야 한다.

기존 프롬프트에는 이미 근거 제한·추측 금지·실행 한계가 있었다. 문구 누락만의 문제라고 설명할 수 없다. 모두 stop으로 끝났으므로 출력 잘림으로도 설명할 수 없다. 문서 부족, 근거 활용 실패, 조건 변형, 유용성 부족을 분리한다.

## 개선 설정의5문항 재검토

새 운영 조건에서 5건 모두 completed/stop, 총149.58초였다. 기존1566.81초와는 샘플링·출력 길이도 달라 캐시 단독 속도 배수로 쓰지 않는다. 순수 속도 비교는 앞의 통제 실험을 따른다.

급여계좌 질문은 퇴사 정책을 섞고 없는 개인 정보 수정 메뉴를 안내했다. 출장 정산 질문은 정적 절차 문서에서 개인 처리 결과를 확인하게 하고, 사용자가 '반려 요청'을 하도록 절차를 뒤집었다. 보안 신고는15분 목표를 보존했으나 '인지 후30분'을 '신고 후30분'으로 바꿨다. VPN은 적절한 자료 부족 안내, 거래처 계좌는 과도한 유보와 직접 실행 불가 설명 누락이 남았다.

따라서 속도 개선과 전반적 품질 개선을 함께 선언할 수 없다. 높은 심각도의 근거·절차·조건 오류가 여전히 있다. 기존/새 출력의 차이를 캐시 압축 단독 효과라고 해석하지 않는다. 전체 주장표와 원문은 tmp의 quality-audit.md 및 q4-quality-judgments.jsonl에 있다.

## 문서 범위·프롬프트8건 비교

RQ0001과RQ0007에 전체71건/수동 관련3~4건, 기존/강화 system을 교차했다. 전체 입력은 약67.7k, 관련 subset은 약3.9k/4.6k다. 문서 없는 메뉴·상태·의무 생성 금지, 목표·주체 보존,3~5문장 제한을 추가했지만 어떤 조건도 두 문항의 문제를 모두 없애지 못했다.

급여계좌 질문은 관련3건+강화에서도 없는 '재무 > 휴가·근태·정산' 메뉴를 발명했다. 전체+강화는 마감·메뉴 부재를 인정하면서059 근태 문서에 계좌 변경이 포함된다고 허위 인용했다. 출장 정산은 관련4건+기존에서 상당히 나아졌지만 문의 채널/순서 표현 오류가 남았다. 강화 prompt는 더 짧아졌으나 새 보완 절차를 추가해 항상 더 낫지 않았다.

긴 문맥이 유일한 원인은 아니며, 모델의 근거 활용·유보 능력을 따로 검증해야 한다. 같은 seed/temperature의 동일 입력도 RQ0001에서 출력이 달랐다. 이 실험은 원인 탐색이며 모델 전체 성능, 실제 검색 품질 또는 완전 재현성을 입증하지 않는다. 상세 조건표는 로컬 tmp의 ablation-review.md 및 ablation-judgments.jsonl을 따른다.

현재 공통 prompt는 유지했다. 다음은 답변 가능성과 필수 근거를 고정한 평가셋 → 근거 추출/최종 답변 분리 검사 → 같은 작은 근거 묶음에서 다른 모델 비교 → 실제 문서 선택기 검증 순서다. LangChain 경로 전체 재작성이나 검색기의 즉시 도입을 채택한 것은 아니다.

## 학습 기록과 다음 판단

작은 모델 파일이 전체 추론 메모리가 아니라는 점, 입력 문맥·KV cache·GPU 배치가 지연을 좌우한다는 점을 실제 로그로 확인했다. 설정값을 바꿨다는 사실보다 backend가 실제 적용했는지가 중요했다. 형식 검사를 통과한 답변도 조직 규칙을 잘못 안내할 수 있어 COMPLETED를 정답률로 쓰지 않는다.

이번 구현·운영 실험과 독립 AI 검토는 위임 수행이다. 사용자의 독립 구현 숙련도나 사람이 검수한 서비스 품질로 확대하지 않는다.

문서 추가 시 새 snapshot/개정/hash를 보존하고 질문+문서+system+출력 예약 예산과 지연을 다시 확인한다. 지금96k 여유가 영구적인 문서 수용 보장은 아니다. 수동 관련문서 실험은 원인 확인용이며 실제 검색기 도입을 증명하지 않는다. 얇은 LangChain 생성 경로는 유지하고, 근거·answerability·조건 보존 평가 후 문서 선택과 더 큰 모델의 필요성을 판단한다.

## 최종 검증과 저장

생성 관련139개 테스트 통과, 전체 Ruff check 통과,194파일 format check 통과, shell 구문 검사 통과. 실제 공통 CLI를 개선11435 서버에 연결해71문서/입력67663/출력44/stop/completed 및 exit0을 확인했다. 경로 내부4.16초·프로세스4.88초는 cache가 남은 호출로 cold 성능이 아니다. 첫 CLI 확인 때 필수 --model을 빠뜨린 명령 오류(exit2)는 보존했고 명령·안내를 고친 뒤 새 파일로 재검증했다.

시스템 기본 서비스는 유지했다. 실험용 서버는 검증 후 종료하고 GPU 메모리를 반환한다. 실행 스크립트로 같은 프로필을 다시 시작할 수 있다. 이번 작업은 로컬 문서와 기존 Notion 개인 일지에 기록하며 새 Git 커밋/원격 게시를 수행하지 않는다.

[Notion 개인 일지](https://www.notion.so/3f905a3cdadc8146a9bbedb690ab5ecf)의 제목·현재 다음 작업·이번 실험 본문·요약 속성을 갱신하고 재조회했다. 이전 학습 기록과 담당자·기간·게시 링크는 보존했으며 새 로컬 문서에 원격 링크를 만들지 않았다. 실험 프로세스 종료 후 GPU 사용량102MiB와 시스템 서비스의 빈 모델 목록을 확인했다.
