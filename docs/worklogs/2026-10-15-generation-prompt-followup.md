# 두 모델의 잔여 오류와 프롬프트 후속 검토

2026-10-15. 사용자 요청에 따라 기존 생성 변경 게시와 추가 조치를 검토했다. 아래 프롬프트는 **제안이며 적용·실모델 검증하지 않았다**. 기준은 [실제 비교](2026-10-15-generation-openai-comparison.md), `generation/prompts.py`, 로컬 `tmp/langchain-generation-review-2026-10-14/03-architecture-decision.md`다. 독립 AI 검토도 원문 정책과 응답을 대조했다.

## 판단

얇은 LangChain 어댑터와 단일 생성 경로를 유지한다. 지금 확인된 실패는 업무 적용 범위, 기록과 조회 권한, 조건·시간 기준을 잘못 연결하는 것이다. 일반적인 “추측하지 말라”를 반복하는 대신 그 경계를 명시하는 최소 변경을 먼저 비교한다. 공식 [프롬프트 안내](https://developers.openai.com/api/docs/guides/prompt-engineering)는 지시·예시·문맥의 명확한 구분과 예시 기반 안내를 설명한다. 이를 이번 관측 오류에 적용한 아래 문구는 프로젝트 제안이며 공식 문서가 이 모델·데이터에서 효과를 입증한 것은 아니다.

## 최소 강화 후보

기존 역할·실행 미지원·문서 속 지시 무시·한국어·JSON 규칙은 유지하고 근거 규칙에 다음을 더한다.

```text
문서의 적용 대상과 업무 상황이 질문과 일치하는 내용만 안내하세요.
다른 업무의 절차를 유사하다는 이유로 옮기지 마세요. 적용 조건이 불명확하면
확인된 내용만 조건부로 설명하거나 필요한 구분을 질문하세요.

문서의 행동 주체, 처리 순서, 시간의 시작점, 목표와 의무, 예외의 조건을
그대로 보존하세요. 기록이 존재한다는 설명으로 사용자의 조회 권한이나
조회 화면을 추정하지 마세요. 일반 문의 창구를 처리 메뉴로 바꾸지 마세요.

질문에서 확인할 수 있는 부분과 없는 부분을 나누어 답하세요.
없는 메뉴·기한·권한·담당 업무를 채우지 말고, 문서에 확인된 일반 문의
창구가 있으면 문의를 제안하되 해당 업무 담당이나 처리 경로로 단정하지 마세요.
```

“문서에 없음”과 “사용자의 상황이 불명확함”은 구분한다. 전자는 자료 부족 안내, 후자는 답변에 필요한 최소 확인 질문이다. 사용자에게 질문해도 없는 정책을 알 수 있는 것은 아니다. 문의 안내는 근거 있는 일반 창구 제안으로 한정한다.

## 대조 예시 후보

규칙만의 효과를 먼저 확인하고, 남는 오류에만2~3개 예시를 별도 후보로 추가한다. 아래는 실회사 정책이 아닌 합성 교육 예시다. 평가 문항의 답을 그대로 예시에 넣지 않는다.

| 주어진 근거 | 질문 | 바람직한 답변 방향 |
|---|---|---|
| 담당자는 자산 접수 결과를 기록한다 | 어디서 접수 결과를 조회하나요? | 직원 조회 화면은 근거에서 확인되지 않음 |
| 신청자는 포털 자산 메뉴의 신청 내역에서 접수 결과를 조회한다 | 어디서 접수 결과를 조회하나요? | 명시된 메뉴와 신청 내역을 구체적으로 안내 |
| A와 B 채널 모두 실패하면 C를 사용한다 | A만 안 되면 C를 쓰나요? | A 실패만으로 두 채널 모두 실패한 조건을 충족하지 않음 |

긍정 사례도 포함하여 모든 질문에 유보하는 퇴행을 방지한다. 문장 수를 강제하여 예외 조건을 잘라내거나, 인용 ID가 존재한다는 것만으로 정답 판정을 하지 않는다. 구조화 출력도 형식 보장과 사실성 평가를 분리한다.

## 추가 조치와 순서

1. 기존5문항을 개발·회귀 세트로 고정한다. 각 문항에 답변 가능성(충분/부분/부족), 필수 주장, 금지 주장, 정확한 근거 구간, 적용 대상·조건을 사람이 확인 가능한 형태로 기록한다. GPT 출력을 정답으로 복사하지 않는다.
2. RQ0006·RQ0009도 강화 비교에 넣고, 답이 명시된 정상 문항과 최소 조건 대조쌍을 추가한다. 전체 문서 snapshot·질문·모델 설정을 고정한다. 이전13회 중 강화 비교는 RQ0001·RQ0007뿐이었다.
3. 모델2개 × baseline/규칙 강화2개를 먼저 비교한다. 같은 문항의 반복은 최소2회부터 확인하되 반복 횟수와 분산을 보고한다. prompt hash는 후보별로 달라야 하며, 동일 입력 비교기는 후보를 섞지 않고 후보별 두 모델 비교에 사용한다.
4. 중대한 근거 오류, 필수 안내 누락, 과잉 유보, 올바른 유보, 형식 실패, 시간·토큰을 별도로 집계한다. 알려진 오류가 줄고 정상 사례가 퇴행하지 않은 후보만 다음으로 넘긴다. 개발에 사용하지 않은 문항으로 최종 확인하며 소수 표본의 무오류를 운영 신뢰성으로 확대하지 않는다. [공식 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 실제 사용 사례·경계 사례·지속 평가 원칙을 따른다.
5. 규칙만으로 부족하면 예시 추가를 비교한다. GPT reasoning 변경은 프롬프트와 동시에 바꾸지 않는 별도 실험으로 둔다.
6. 그래도 범위 오류가 남으면 문서 ID·짧은 근거 인용·적용 범위·조건 추출 후 답변하는2단계 후보를 검토한다. 인용 원문 일치 검사는 가능하지만 적용 타당성까지 증명하지 않는다. 추가 호출의 비용·지연·추출 오류를 측정한 뒤 채택한다. LangGraph나 전면 재작성은 선행 조건이 아니다.

검색은 문서 증가·입력 예산·지연·불필요한 문맥 문제를 해결하는 별도 축이다. 관련문서만 줘도 Qwen 오류가 남았으므로 검색만으로 해결된다고 가정하지 않는다. 검색 시 정책의 적용 범위·조건·예외를 본문과 함께 유지하고 검색 근거 누락과 생성 왜곡을 구분한다.

급여계좌 변경 메뉴·마감, VPN 승인 조회·알림, 신고자의 기록 접근 권한은 확인된 정책이 부족하다. 담당자가 확인한 실제 정책이 생기면 원문을 갱신하고 새 snapshot/hash·평가 기대값을 함께 바꾼다. 모델의 추정으로 정책을 생성하거나 ai_reviewed를 사람 승인으로 바꾸지 않는다.

## 게시 범위와 검증

공유 작업 트리의 다른 분류 커밋·스테이징을 보존하기 위해 원격 main 기반의 생성 전용 브랜치에서 게시한다. API 키와 tmp 원자료는 게시하지 않는다. 원자료 해시·설정·핵심 관측은 기존 비교 일지에 남긴다.

게시 전 오류 로그 검토에서 provider 예외 원문이 출력되는 부분을 발견해 오류 종류만 출력하도록 제한했다. 비밀값을 포함한 합성 예외가 노출되지 않는 회귀 테스트로 검증한다. 이 변경 외에 이번 검토안으로 제품 프롬프트나 파이프라인을 변경하지 않는다.
