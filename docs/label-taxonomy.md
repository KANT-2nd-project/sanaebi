# 분류·라벨링 기준

- 버전: 1.0
- 기준일: 2026-10-13
- 적용 범위: 직원 300명 이상의 기업용 업무·협업 SaaS 개발·운영 기업 이음웍스를 가정하고, 흩어진 전사 공통 규정·절차를 찾아 구성원의 반복 문의를 줄이는 사내비 프로젝트
- 초기 학습 대상: 문서 제목과 본문으로 업무 주제를 분류하는 다중 라벨 분류 1종
- 팀 기획·진행 문서: [Notion 프로젝트 메인](https://app.notion.com/p/c8666c5724218381b3a501609274e325)

이 문서는 초기 라벨과 라벨링 기준, 질문의 서비스 처리 기준을 정한다. 문서 분류 라벨은 프로젝트 목적에 맞춘 결정이며 업계 공통의 고정 분류 체계를 뜻하지 않는다. 이번 변경은 정의서 반영이며 데이터 작성·모델 학습·API·서비스 구현 완료를 뜻하지 않는다.

## 라벨링 단위와 공통 원칙

1. 한 문서의 제목과 본문을 함께 읽고, 작성 부서나 파일 형식이 아니라 실제 내용으로 판단한다.
2. 해당 주제에 관한 독립적이고 실질적인 안내·규칙·절차가 있을 때만 라벨을 붙인다. 다른 주제를 설명하면서 단어만 언급한 경우에는 붙이지 않는다.
3. 한 문서가 여러 주제를 각각 실질적으로 다루면 라벨을 함께 붙인다. 라벨 수를 하나로 제한하지 않는다.
4. 내용이 부족하거나 분류 기준이 해결되지 않으면 추측해 라벨을 만들지 말고 **검토 보류**로 둔다. 현재 체계로 표현하기 어려운 정상 업무 문서는 **확장 후보**로 기록해 분류 체계를 검토한다.
5. 검토 보류·확장 후보 문서는 정답 확정 전 학습·평가용 정답 데이터에서 제외한다. 이러한 관리 상태는 업무 주제 라벨이 아니다.
6. `OTHER`, `기타`, `OOS` 토픽 라벨은 두지 않는다. 라벨이 하나도 없다는 이유만으로 문서나 질문을 범위 밖이라고 가정하지 않는다. 미분류 문서는 원인을 확인하고 보류 또는 taxonomy 검토 대상으로 처리한다.
7. 기존 자료에 있는 4개 라벨은 v1.0에 자동 대응시키지 않는다. 원문을 다시 검토해 이 기준으로 재라벨링한다.

## 라벨

| 라벨 ID | 이름 | 대표 문서 |
|---|---|---|
| `HR` | 인사·근무·복지 | 연차 신청 규정 |
| `IT` | 계정·업무도구·IT 지원 | VPN 연결 절차 |
| `FINANCE_PROCUREMENT` | 비용·구매·정산 | 출장비 정산 규정 |
| `WORKPLACE` | 총무·시설·사무환경 | 방문객 출입 안내 |
| `SECURITY_LEGAL` | 보안·개인정보·법무 | 개인정보 외부 공유 기준 |
| `COMPANY` | 회사·조직 안내 | 조직도와 팀 역할 안내 |

### `HR` — 인사·근무·복지

- **포함:** 직원 휴가와 근태, 근무 제도·일정, 복지, 직원 급여, 입사·퇴사 절차와 인사 서류.
- **제외:** 계정 발급·접근과 업무 도구 설정은 `IT`; 직원 경비와 협력사 지급은 `FINANCE_PROCUREMENT`; 사원증의 사무실 출입 기능은 `WORKPLACE`.
- **긍정 예:** 연차 신청 규정, 근태 정정 절차, 복지 포인트 안내, 급여 명세서 확인법, 입사 서류 제출 안내.
- **경계 예:** 입사 체크리스트가 인사 서류와 휴가 제도를 설명하면 `HR`을 붙인다. 같은 문서의 계정 신청 절차는 `IT`, 사원증으로 사무실에 들어가는 안내는 `WORKPLACE`도 붙인다.

### `IT` — 계정·업무도구·IT 지원

- **포함:** 계정 생성·로그인·권한 요청, 업무용 소프트웨어와 협업 도구, VPN, 기술 지원, 업무 기기 설정·문제 해결.
- **제외:** 구매 승인과 지출·공급업체 정산은 `FINANCE_PROCUREMENT`; 정보 취급·외부 공유 규칙과 보안 사고 대응은 `SECURITY_LEGAL`; 사무실 출입은 `WORKPLACE`.
- **긍정 예:** SSO 로그인 안내, VPN 연결 절차, 협업 도구 사용법, 노트북 초기 설정과 기술 문의 절차.
- **경계 예:** 계정 권한을 신청하는 방법은 `IT`; 어떤 정보에 누가 접근해야 하는지 정하는 보안 통제 규칙은 `SECURITY_LEGAL`도 붙일 수 있다. 새 노트북 구매 승인은 `FINANCE_PROCUREMENT`이다.

### `FINANCE_PROCUREMENT` — 비용·구매·정산

- **포함:** 직원 경비, 출장비 정산, 법인카드, 구매 요청·승인, 세금계산서와 청구서, 협력사 대금 지급.
- **제외:** 직원 급여·복지와 직원 자격 요건은 `HR`; 기기 설정과 장애 해결은 `IT`.
- **긍정 예:** 영수증 첨부와 경비 청구 절차, 출장비 한도, 법인카드 사용·정산, 구매 승인 흐름, 협력사 청구서 처리.
- **경계 예:** 출장 경비의 신청·정산 규칙은 `FINANCE_PROCUREMENT`; 출장 중 근무 일정이나 휴가 제도는 `HR`이다. 공급업체 계좌 변경을 승인하는 절차는 지급 통제 내용에 따라 `FINANCE_PROCUREMENT`과 `SECURITY_LEGAL`을 함께 붙일 수 있다.

### `WORKPLACE` — 총무·시설·사무환경

- **포함:** 사무실·물리 공간 출입, 좌석, 회의실, 주차, 사무용품, 우편물, 시설 이용과 문의.
- **제외:** 계정 로그인이나 기기의 기술 설정은 `IT`; 구매 예산과 승인 절차는 `FINANCE_PROCUREMENT`; 근태와 근무 제도는 `HR`.
- **긍정 예:** 사원증으로 사무실에 출입하는 방법, 좌석 예약, 회의실 이용, 주차 신청, 우편물 수령과 사무용품 비치 안내.
- **경계 예:** 사원증 분실 시 사무실 출입 조치는 `WORKPLACE`; 계정 잠금 해제는 `IT`; 출입증 분실에 따른 보안 사고 신고·대응 규칙이 별도로 안내되면 `SECURITY_LEGAL`도 붙인다.

### `SECURITY_LEGAL` — 보안·개인정보·법무

- **포함:** 정보 취급·보관·외부 공유, 개인정보 보호, 보안 통제와 사고 대응, 계약 검토, 윤리·준법 절차.
- **제외:** 모든 회사 정책을 포괄하는 라벨이 아니다. 계정 사용법은 `IT`; 일반 사무실 운영은 `WORKPLACE`; 내용상 보안·법무 주제가 없는 인사 규칙은 `HR`이다.
- **긍정 예:** 개인정보 처리와 파기, 외부 파일 공유 기준, 보안 사고 신고, 계약서 검토 흐름, 이해 상충·윤리 신고 안내.
- **경계 예:** MFA 등록 방법만 설명하면 `IT`; MFA 의무와 보안 통제 이유를 정한 정책이면 `SECURITY_LEGAL`도 붙인다. 계약서 결재의 지급·구매 절차는 `FINANCE_PROCUREMENT`도 붙일 수 있다.

### `COMPANY` — 회사·조직 안내

- **포함:** 회사 소개, 조직과 역할, 공식 소통 채널 등 회사의 구조와 기본 안내.
- **제외:** 다른 라벨을 대신하는 포괄 라벨이 아니다. 주제별 정책·절차는 해당 라벨을 붙이고, 회사 이름이 문서에 나온다는 이유만으로는 붙이지 않는다.
- **긍정 예:** 회사의 사업과 조직 구성 소개, 조직도와 팀 역할, 공식 공지·문의 채널 안내.
- **경계 예:** 조직도와 함께 각 팀의 대표 문의 채널을 안내하면 `COMPANY`; 휴가 신청 담당자만 적힌 휴가 규정은 `HR`이다. 사무실 좌석 문의 채널은 `WORKPLACE`이다.

## 경계 사례와 별도 상태

### 입사 안내 문서

인사 서류와 입사·퇴사 절차는 `HR`, 계정·업무 도구 설정은 `IT`, 사원증을 이용한 사무실 출입은 `WORKPLACE`다. 세 항목이 각각 실질적으로 안내되면 문서 하나에 세 라벨을 모두 붙인다. 작성 주체가 인사팀이라는 이유로 문서 전체를 `HR` 하나로 고정하지 않는다.

### 협력사 청구서

청구서 접수와 지급 절차는 `FINANCE_PROCUREMENT`; 청구서에 개인정보·계좌 정보를 안전하게 다루는 규칙이 별도로 있으면 `SECURITY_LEGAL`도 붙인다. 단순히 청구서에 계좌번호가 들어 있다는 이유만으로 보안 라벨을 추가하지 않는다.

### 질문 처리 개념과 혼동하지 않기

문서 주제 라벨과 사용자 질문의 지원 범위를 구분한다. 아래 내용은 서비스 처리 기준이며, 구현 방식은 후속 단계에서 정한다.

- `IN_SCOPE`: 지원하는 전사 공통 규정·절차에 대한 정보 안내 요청이면 검색을 진행한다. 업무 주제뿐 아니라 요청한 기능도 현재 지원 범위인지 확인한다.
- `OUT_OF_SCOPE`: 주제가 무관하거나 현재 지원하지 않는 기능을 요구하는 것이 분명하면 범위 안내를 한다.
- `UNCLEAR`: 대화 맥락을 살핀 뒤에도 판단이 어려우면 사용자에게 확인한다.

검색을 마친 뒤 근거 문서를 찾지 못한 상태는 검색 결과 상태로 별도 기록한다. 이를 질문이 범위 밖이라는 판정과 합치지 않는다. 인사말은 짧게 응답하고, 빈 입력과 시스템 오류도 각각 별도 입력·오류 상태로 다룬다. 문서 토픽 분류 모델을 질문 범위 판정기로 간주하지 않으며, 이번 초기 학습 과제에 별도의 질문 분류 모델을 추가하지 않는다.

| 질문·상황 예시 | 판단 | 처리 |
|---|---|---|
| “우리 회사 연차 신청 절차 알려줘.” | `IN_SCOPE` | 관련 회사 자료를 검색한다. |
| “김치찌개 만드는 법 알려줘.” | `OUT_OF_SCOPE` | 사내 규정·업무 절차를 안내하는 서비스임을 알린다. |
| “내일 연차를 신청해 줘.” | `OUT_OF_SCOPE` | 실제 신청은 현재 지원하지 않음을 알리고 신청 절차는 안내할 수 있음을 설명한다. |
| “내 남은 연차를 조회해 줘.” | `OUT_OF_SCOPE` | 개인의 실시간 인사 정보 조회는 현재 지원하지 않음을 안내한다. |
| 대화 맥락 없이 “그거 어떻게 해?” | `UNCLEAR` | 어떤 업무나 절차를 뜻하는지 되묻는다. |
| “장기근속 포상 기준은?”에 대해 정상 검색 후에도 근거를 확보하지 못함 | `IN_SCOPE` + 근거 부족 | 확인할 자료가 없음을 알린다. 담당자 정보가 등록된 경우에만 문의 경로를 제공한다. |

분류 점수가 낮다는 사실만으로 지원 범위 밖이라고 단정하지 않는다. 점수가 높아도 답변 근거가 있다는 뜻은 아니다. 근거 부족은 분류 점수만으로 결정하지 않으며, 검색 실패 같은 시스템 오류와도 구분한다.

토픽 라벨은 선택적 검색 메타데이터로 활용할 수 있지만, 검색을 특정 토픽 라벨로 미리 차단하는 하드 필터로 사용하지 않는다.

## 확장 후보와 버전 관리

개발·서비스 운영 지식은 후속 업무 영역 후보로 둔다. 업무 실행과 개인의 실시간 정보 조회는 후속 기능 확장으로 구분한다. 기능이 늘어난다고 바로 문서 주제 라벨을 추가하지 않으며, 실제 문서와 사용 사례에 따라 주제 체계 또는 질문 처리 경로를 검토한다.

라벨 ID는 안정적으로 유지한다. 새 라벨 추가, 분할, 병합, 의미 변경은 버전을 올리고 변경 이유와 영향받는 기존 데이터를 기록한 뒤 재검토·재라벨링한다. 표시 이름이나 예시를 다듬더라도 의미가 달라졌다면 의미 변경으로 취급한다.

모델 종류, 데이터 규모, 데이터 분할 비율, 분류 임계값, API 경로는 이 문서에서 정하지 않는다. 실험으로 확인하지 않은 값을 정해진 설계처럼 기재하지 않는다.

## 향후 평가 원칙

다중 라벨 평가는 micro·macro F1과 라벨별 precision·recall을 함께 보고, 오분류 사례를 검토한다. 원문, 복사본, 개정본, 청크처럼 같은 출처 문서 계열에 속한 데이터는 학습·검증·테스트 중 한 분할에만 둬 데이터 누수를 막는다. 임계값이나 모델 선택은 검증 세트에서 하고, 최종 테스트 결과는 선택을 마친 뒤 평가한다.

이 문서의 사례는 라벨링 기준을 설명하기 위한 예시다. 이번 변경에서는 실제 학습용 데이터 작성·재라벨링, 모델 학습, 서비스 구현·실행 검증을 수행하지 않았다.
