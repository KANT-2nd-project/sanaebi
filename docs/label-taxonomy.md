# 요청 처리 분류·라벨링 기준 v1.0

- 기준일: 2026-10-14
- 적용 대상: 요청 처리 데이터셋 v0.1과 질문 처리 분류기
- 적용 데이터와 기록: [요청 처리 데이터 안내](../data/README.md)
- 서비스 흐름: [서비스 아키텍처](service-architecture.md)

## 분류 목적과 입력

라벨은 회사 업무 질문의 주제가 아니라 질문 다음에 어떤 처리를 할지 나타낸다. 입력은 현재 사용자 발화 하나다. 이전 대화 이력은 사용하지 않는다. 데이터셋의 `question` 열만 모델 입력으로 사용하고, ID·정답·그룹·출처·검수 정보는 입력에서 제외한다.

선택적 `gate`에서 분류 결과는 질문을 처리할 경로다. 기본 `advisory`에서는 오류 가능한 생성 참고 정보로, 명시적 `shadow`에서는 관찰 기록으로만 사용하며 이 문서의 라벨 정의와 기존 데이터 정답을 바꾸지 않는다. [서비스 모드 설명](service-architecture.md#분류-관찰-모드)을 참고한다. SEARCH_KNOWLEDGE를 골랐다고 해서 회사 문서에 답이 있거나 답변 근거가 확보된 것은 아니다. 문서 확인 뒤 실제 답을 찾지 못하면 자료 부족을 알려야 한다. 낯선 용어, 짧은 표현, 실제 근거 문서의 부재만으로 CLARIFY나 UNSUPPORTED를 부여하지 않는다.

## 라벨 정의

아래 처리 열은 라벨의 의도와 gate에서의 분기 기준이다. 기본 advisory와 명시적 shadow는 라벨로 생성을 차단하지 않고 문서 기반 생성기가 안내·재질문·범위를 판단한다.

| 라벨 | 적용 기준 | 처리 |
|---|---|---|
| `SEARCH_KNOWLEDGE` | 회사 규정·절차·조직·공통 업무도구에 관한 정보 요청. 짧거나 일반적인 안내 요청, 낯선 사내 용어 설명 요청도 포함한다. | 문서에서 답변을 시도한다. 문서에 정보가 없으면 근거 부족을 알린다. |
| `CLARIFY` | 현재 발화만으로 가리키는 대상이나 원하는 도움을 정할 수 없다. 정보 안내를 원하는지 실제 실행을 원하는지도 불분명할 수 있다. | 필요한 대상이나 의도를 구체적으로 묻는다. |
| `UNSUPPORTED` | 개인·조직의 실시간 기록을 조회하거나 실제 업무를 실행·변경하라는 요청, 또는 회사 업무와 무관한 요청이다. | 현재 지원 범위를 안내한다. |

`SEARCH_KNOWLEDGE`는 회사 지식을 찾아 답변을 시도하는 경로다. 서버는 SQLite 게시 snapshot을, 독립 CLI는 JSON Lines snapshot을 같은 문서 렌더러로 생성 흐름에 전달한다. 이 라벨 자체는 근거 존재나 RAG 구현 여부를 뜻하지 않는다. 서버는 기본 rag(C)와 명시적 full를 구현했으며 [현재 문서 공급 정책](service-architecture.md#검색-근거-구성)을 따른다.

## 판정 순서와 경계 규칙

1. 회사 정보나 절차를 명시적으로 묻는 부분이 있으면 `SEARCH_KNOWLEDGE`로 보낸다. 요청이 짧거나 포괄적이어도 유용한 일반 안내를 할 수 있으면 되묻지 않는다.
2. 사용자가 자신의 상황을 직접 설명하고 그 상황에 규정을 적용해 달라고 묻는 경우 `SEARCH_KNOWLEDGE`다. 제공한 상황을 설명하는 일과 회사 기록을 조회하는 일은 구분한다.
3. 정보 요청에 실제 실행이나 개인·조직의 실시간 기록 조회가 함께 있어도 `SEARCH_KNOWLEDGE`로 보낸다. 답변은 안내 가능한 정보만 제공하고 조회·실행할 수 없는 부분을 분명히 밝힌다.
4. 질문이 오직 실제 실행·기록 변경·실시간 조회만 요구하면 `UNSUPPORTED`다. 실행에 필요한 날짜나 세부 조건이 빠졌더라도 실행 의도가 분명하면 되묻지 않는다.
5. 어떤 대상을 말하는지, 또는 정보 안내와 실행 중 무엇을 원하는지 판단할 수 없을 때 `CLARIFY`를 선택한다.
6. 회사 업무와 명확히 무관한 요청은 `UNSUPPORTED`다.

판정은 단어 하나나 문장 길이가 아니라 요청의 뜻을 따른다. 회사 문서에 실제 근거가 있는지, 분류 모델이 확신하는지는 이 라벨의 기준이 아니다.

## 경계 사례

| 질문 | 라벨 | 이유와 처리 |
|---|---|---|
| “연차 신청 방법 알려줘.” | `SEARCH_KNOWLEDGE` | 절차 안내 요청이다. |
| “휴가를 어떻게 써?” | `SEARCH_KNOWLEDGE` | 짧은 일반 안내 요청이다. |
| “내가 입사한 지 8개월 됐어. 회사 휴가 발생 기준을 내 상황에 적용하면 어떻게 돼?” | `SEARCH_KNOWLEDGE` | 사용자가 제공한 상황에 회사 규정을 적용해 달라는 요청이다. |
| “블루데이 제도 알려줘.” | `SEARCH_KNOWLEDGE` | 낯선 제도명이어도 문서에서 확인한다. |
| “미등록된 장기근속 포상 기준 알려줘.” | `SEARCH_KNOWLEDGE` | 근거가 없으면 자료 부족을 알린다. |
| “내 연차 잔여일은 어디서 확인해?” | `SEARCH_KNOWLEDGE` | 조회 방법을 묻는다. |
| “휴가 규정 알려주고 내 잔여일도 조회해줘.” | `SEARCH_KNOWLEDGE` | 규정 정보만 안내하고 개인 기록은 조회하지 못한다고 밝힌다. |
| “휴가 신청 방법 알려주고 다음 주로 등록해줘.” | `SEARCH_KNOWLEDGE` | 신청 방법만 안내하고 등록 실행은 하지 않는다. |
| “내 연차가 며칠 남았어?” | `UNSUPPORTED` | 개인의 실시간 기록 조회 요청이다. |
| “내일 연차 신청해줘.” | `UNSUPPORTED` | 실제 신청 실행 요청이다. 날짜가 명시되어도 실행할 수 없다. |
| “연차 신청해줘.” | `UNSUPPORTED` | 실행 의도가 분명하다. 실행 정보가 빠졌어도 `CLARIFY`로 바꾸지 않는다. |
| “김치찌개 만드는 법 알려줘.” | `UNSUPPORTED` | 회사 업무와 무관한 요청이다. |
| 앞선 맥락 없이 “그거 어떻게 해?” | `CLARIFY` | 가리키는 대상이 없다. |
| “휴가 신청 도와줘.” | `CLARIFY` | 절차를 묻는지 신청 대행을 원하는지 알 수 없다. |
| “이 제도를 어떻게 적용하면 될까?” | `CLARIFY` | 어떤 제도를 말하는지 현재 발화로 특정할 수 없다. |

명시적인 정보 요청과 미지원 요청을 함께 처리할 때는 답변 경로를 유지한다. 이 라벨은 업무 실행이나 개인 기록 조회를 허용하지 않는다. 반대로 순수 실행 명령에 정보 안내 의도를 추측해서 추가하지 않는다.

순수 인사말과 빈 질문은 학습 데이터에 포함하지 않는다. 인사말과 실질 질문이 함께 있으면 실질 요청에 따라 분류한다. API는 빈 문자열이나 공백만 있는 질문을 HTTP 422로 거부한다.

## 데이터 적용

이 기준은 요청 처리 데이터셋의 라벨 의미를 정한다. 모델 입력은 현재 질문 하나이며, 데이터의 구성·검수·분할·검증 상태는 [데이터 안내](../data/README.md)에서 확인한다. 기준 문서만으로 데이터 검수, 모델 학습 또는 서비스 구현이 완료됐다고 볼 수 없다.

## 기준의 변경

새 예시를 추가해도 기존 라벨의 뜻을 바꾸지 않도록 한다. 라벨 의미를 변경하거나 라벨을 추가·병합할 때는 기준 버전을 올리고, 영향받는 질문을 다시 검토한다. 라벨 경계가 달라지면 이전 점수와 새 기준의 점수를 같은 결과로 취급하지 않는다.

## 라벨의 생성 전달 실험

모든 라벨에 같은 지침을 주고 값만 전달한 비교에서 실제 라벨의 추가 이득을 확인하지 못했다. 라벨별 생성 지침·모델·문서 설정은 채택하지 않았으며, 라벨 의미와 명시적 shadow/gate 동작은 유지한다. 이후 사용자의 설계 결정으로 동일 공통 지침+서버 예측 라벨 C를 advisory 기본값에 연결했다. SEARCH는 근거 존재를 보장하지 않고 CLARIFY는 재질문을 강제하지 않으며 UNSUPPORTED는 전체 거절·일반 지식 허용 명령이 아니다. `/assistant`의 client 라벨은 전달하지 않는다. [후속 채택 기록](worklogs/2026-10-16-adopt-advisory.md)을 따른다. [평가 결과](../generation_evaluation/reports/2026-10-15-classification-advisory/README.md)에서 분모·비용·한계를 확인할 수 있다.
