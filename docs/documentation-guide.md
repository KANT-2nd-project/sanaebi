### README 편집 기준

루트 README의 주 독자는 처음 방문한 사용자·팀원이다. 서비스 목적·사용 모습·주요 기능·간단한 처리 흐름·현재 구성·빠른 시작·상세 문서를 중심으로 소개한다. 서버 입문은 요청 처리와 API 확인, 추론 안내는 계산·로딩·독립 확인, 실험 문서는 학습·평가·선정 근거를 담당한다. 공통 설치·통합 실행은 루트, 전문 준비·운영 절차는 하위 문서에 둔다.

- **정보 배치:** 최소 준비 조건은 시작 안내 옆에 남기고 상세 준비 절차로 연결한다. 프로세스 종료·curl·오류 상세·작업 경위는 해당 실행 안내나 기록에 둔다. 루트에서 상세 문서로 보냈다가 같은 준비 설명을 찾으러 루트로 되돌아오는 순환을 만들지 않는다.
- **현재 구성:** 선정 모델, 코드 기본값, 실제 실행 확인을 구분한다. 모델 표에는 역할·상태·근거 링크를 두며 성능표·설정표·검증 로그는 각각의 기준 위치에서 관리한다. 실험 결과만으로 서버 교체나 서비스 품질 검증을 주장하지 않는다.
- **화면과 그림:** 루트는 사용 흐름, 서버는 요청 순서, 추론은 계산을 보여준다. 화면 캡처·모의 응답·실제 모델 응답을 구분하고 캡션·대체 텍스트를 작성한다. 제작 전에는 설명과 HTML 주석으로 위치만 남기며 없는 이미지 링크나 성공 주장으로 채우지 않는다.
- **링크와 독자:** 실행 문맥에는 짧은 ‘상세 절차’ 링크를 사용한다. 서로 다른 대상을 나열할 때는 목적을 구별할 수 있는 이름을 쓴다. 하위 문서는 상위·관련 기준을 상대 링크로 연결한다.
- **적용 범위:** 위 항목은 역할과 판단 기준이다. 모든 README에 같은 목차·그림·검증 로그를 강제하지 않으며 짧은 색인·보관 안내에도 불필요한 절을 추가하지 않는다.

제목·위치를 바꾸면 변경 문서의 나가는 링크뿐 아니라 현재 문서에서 들어오는 링크·앵커도 확인한다. 표·Mermaid와 HTML 주석의 실제 렌더링, 신규 사용자의 시작 경로와 담당자의 상세 절차 도달 여부를 검수한다. 역사 기록의 고정 커밋 링크는 당시 문서를 기준으로 판단하며 일괄 갱신하지 않는다. 수행한 정적 검사·렌더링·실행과 미확인 항목은 작업 기록에서 구분한다.

## Notion 대응표

이 표의 기술 문서는 Git 기준의 요약·링크를 Notion에 반영한다. Notion의 담당·기한·상태·회의 기록은 해당 페이지가 기준이다. 기술 문서 변경을 수행하는 사람이 영향을 받는 요약도 확인하며, 기준의 의도가 충돌하면 해당 항목을 팀 리더와 조율한다.

페이지 제목은 탐색 단서다. 수정할 때는 위 ID의 본문과 부모 경로를 확인한다. 같은 ID의 용도가 과거와 달라졌다면 이전 결과를 그 페이지의 현재 내용으로 설명하지 않는다. 과거 문서 분류 기준은 [보관 기준](../data/archive/document-topics-v0.2/label-taxonomy.md)처럼 버전이 구분되는 자료로 연결한다.

API 명세나 다른 작업까지 영향을 받으면 해당 페이지·DB 스키마를 읽고 그 변경에 필요한 범위만 추가한다. 문서 정리만으로 담당·기한·상태나 데이터베이스 구조를 일괄 변경하지 않는다.

## 갱신 절차

1. 요청과 기존 대화에서 조사·문서 수정·Notion 반영·상태 변경·커밋·푸시의 범위를 확인한다. 조사 요청이면 지정된 보고서만 작성한다.
2. 현재 브랜치·커밋·작업 트리, 관련 기준 파일과 대상 페이지를 읽는다. 이번 사실의 기준 위치와 수정할 구역을 정한다. 단순 오타 수정에 전체 공간 조사를 요구하지 않는다.
3. 기준 문서를 먼저 수정하고 관련 요약을 갱신한다. 동일 사실을 여러 원본에서 수동 관리하지 않는다. 기본 연결 방식은 링크와 짧은 요약이다.
4. 같은 파일·페이지는 한 작성자가 맡는다. 저장 직전에 대상 내용을 다시 읽고, 읽은 이후 다른 변경이 생겼으면 관련 부분을 재대조한다. 기존 변경을 보존하고 판단할 수 없는 의도 충돌만 조율한다.
5. 변경한 명령·예시·스키마와 양방향 상대 링크·앵커, 표·그림·주석 렌더링 및 독자별 탐색 경로를 확인한다. 실행하지 않은 예시와 검사는 실행 완료로 기록하지 않는다.
6. Notion은 영향받는 구역만 수정하고 본문·핵심 링크·변경한 속성을 재조회한다. 무관한 내용·댓글·담당·기한·역사 기록은 보존한다. 응답이 잘리거나 지원하지 않는 블록이 있으면 확인 범위를 제한해서 보고한다.
7. 실제 diff와 결과를 대조하고 성공·실패·미확인 대상을 작업 보고에 남긴다. 외부 링크가 새 Git 파일을 가리키면 해당 파일이 원격에 게시된 뒤 링크를 반영한다.

반드시 동일해야 하는 작은 표를 복제할 필요가 생기면 원본·대상 구역·방향을 먼저 정한다. Git 파일과 Notion 페이지 전체의 양방향 자동 복제를 기본으로 삼지 않는다.

### 작업 상태와 역사 기록

상태 변경이 요청 범위에 포함되면 해당 작업의 완료 기준과 실제 산출물을 대조한다. 설계 확정, 데이터 작성·AI 검수, 사람 승인, 구현, 실행, 모델 평가를 각각 구분한다. 문서 갱신이나 분할 dry-run을 모델 학습·서비스 완성으로 처리하지 않는다.

현재 안내 링크는 최신 기준을 가리킨다. 과거 실행 결과는 해당 커밋이나 식별 가능한 보관 자료로 연결하고 수치·날짜·당시 한계를 유지한다. 정정이 필요하면 근거를 연결한 후속 정정으로 남긴다. 담당자·승인·성능 수치를 추정하지 않는다.

### 부분 실패와 재시도

Git과 Notion의 쓰기는 하나의 트랜잭션이 아니다. Git 반영 후 일부 페이지가 실패하면 성공한 변경을 유지하고 남은 페이지와 이유를 기록한다. 저장 응답을 받지 못했으면 실제 반영 여부부터 조회하고 누락된 작업만 재시도한다. 생성 여부가 불확실한 페이지나 일지를 다시 만들지 않는다.

재시도 전 기준과 대상의 변경 여부를 다시 확인한다. 접근 오류·해결되지 않은 충돌이 계속되면 해당 대상의 갱신을 멈추고 필요한 조치를 보고한다. 404만으로 삭제를 단정하거나 대체 페이지를 만들지 않는다. 재조회는 잠금이나 원자적 갱신을 보장하지 않는다.

## 규약과 작업 기록의 유지

공통 문서 원칙과 `project-doc-sync` 스킬은 dotfiles에서 관리한다. 이 저장소의 [AGENTS.md](../AGENTS.md)와 이 가이드는 프로젝트별 기준과 대응표를 관리한다. 스킬은 필요할 때 사용하는 절차이며, 설치되지 않은 환경에서도 이 가이드로 작업할 수 있다.

개별 작업에는 필요에 따라 목적, 기준 커밋, 대상 페이지·구역, 반영 결과, 확인 시각, 검증 근거, 남은 항목을 기록한다. 작은 수정마다 별도 보고 파일이나 해시를 강제하지 않는다. 임시 조사 폴더 전체를 상시 지침이나 서비스 명세로 연결하지 않는다.

원본 위치나 페이지 역할을 바꾸는 작업은 이 대응표와 관련 링크도 갱신한다. 가이드 자체를 변경할 때도 동일한 검토·검증 절차를 따른다.
