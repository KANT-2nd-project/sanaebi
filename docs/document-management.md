# 로컬 문서 등록·관리

문서 관리 화면은 `/admin/documents`다. 제목·본문을 붙여 넣어 초안을 저장하고, 편집·게시·사용 중단할 수 있다. 현재 기능은 **로컬 가상 공통 자료 시연용**이며 사용자 인증이나 부서별 접근 권한은 제공하지 않는다. 관리와 답변 생성은 같은 SQLite 저장소를 사용한다. `/ask`·`/assistant`는 현재 유효한 게시본만 답변에 전달한다. 독립 generation CLI는 별도로 내보낸 JSONL snapshot을 사용한다.

## 찾기·읽기·편집

목록은 최근 수정순으로 20건씩 표시한다. 데스크톱 표와 모바일 세로 목록에서 제목, 답변 사용 여부, 수정 초안 여부, 최근 수정일을 확인한다. 목록 주 제목·부서는 기본 읽기와 같은 게시본 기준이며 게시본이 없으면 초안을 쓴다. 다른 초안 제목은 보조 정보로 함께 표시한다. 사용 중단이면 마지막 게시본임을 표시한다. 제목을 선택하면 읽기 화면이 열린다. 게시본이 있으면 기본으로 표시하며 다른 수정 초안이 있을 때만 개정 선택 버튼이 나타난다. 사용 중단 문서는 마지막 게시본을 읽을 수 있지만 답변에서는 제외된다.

제목·본문·시행일·검수 상태는 선택한 개정의 정보다. 본문과 충돌 안내의 서버 최신 초안은 채팅과 같은 Markdown으로 표시한다. 제목·메타데이터는 일반 텍스트다. 강조·목록·표·코드·일반 줄바꿈을 지원하고 제목은 h3 이하로 표시한다. 원시 HTML은 무시하고 이미지는 대체 텍스트만 표시한다. 절대 HTTP/HTTPS 링크만 새 탭으로 연결하며 다른 링크는 텍스트로 남긴다. 출처·검수 정보는 펼쳐서 확인한다. 내부 식별값·본문 해시·이관 추적 정보는 화면에서 노출하지 않고 API와 운영 자료로 확인한다. 게시는 검수 승인과 다르며, ‘게시본 공급 연결됨’도 모델의 실제 답변 성공을 뜻하지 않는다. 연결 상태·모델 가용성·인증 미구현 등 개발 상태는 사용자 화면에 표시하지 않고 이 문서에서 관리한다. capabilities API 계약은 유지하지만 화면에서 조회하지 않는다.

신규 작성·초안 편집 화면만 최대 1600px로 넓힌다. 목록·읽기는 기존 최대 1120px를 유지한다. 1024px 이상에서는 왼쪽 제목·원문과 오른쪽 제목·본문 미리보기를 같은 폭으로 배치한다. 편집 영역은 화면 높이에 따라 늘어나고 본문 공간은 최소 320px를 확보한다. 낮은 화면은 페이지 스크롤을 허용하며 양쪽 패널은 독립적으로 스크롤된다. 미리보기 읽기 폭은 최대 720px다. 좁은 화면에서는 편집·미리보기 탭을 사용한다. 방향키·Home·End로 탭을 이동할 수 있고, 전환해도 입력·선택 영역·스크롤을 보존한다. 제목 또는 본문 오류가 있으면 편집 탭에서 오류를 수정한다. 제목은 일반 텍스트로 미리보고 본문과 별도 필드로 저장한다. 취소·초안 저장은 하단에 붙는 작업 영역에서 제공한다.

`@uiw/react-md-editor`의 편집 전용 화면을 사용하며 Ctrl/Cmd+B·I·K로 굵게·기울임·링크를 삽입한다. 목록에서 Enter는 다음 항목을 이어 쓰고 Tab은 포커스를 이동한다. 실행 취소·다시 실행은 브라우저 편집 이력을 사용한다. 서식 도구는 제목 H2·굵게·기울임·글머리 목록·번호 목록·인용·링크·코드 블록을 삽입한다. 선택 영역을 감싸거나 줄 앞에 기호를 추가하며 이미 적용한 서식을 해제하지는 않는다. 링크 삽입 후 예시 URL을 수정한다. 저장 중에는 입력·도구를 사용할 수 없으며 붙여넣기·도구·단축키 등으로 50,000자를 넘으면 원문을 유지하고 안내한다. 미리보기는 저장 전 입력을 보여주고 저장 요청은 Markdown 원문을 그대로 전달한다. 자동 저장·스크롤 동기화·세션 저장은 하지 않는다.

‘초안 편집’에서 수정하고 명시적으로 저장한다. 저장 후 저장된 초안의 읽기 화면에서 내용을 검토한다. 자동 저장은 하지 않는다. 게시 확인창은 교체 대상 개정·초안·시행일·검수 상태를 보여준다. 같은 개정이 이미 게시 중이면 재게시할 수 없다. 사용 중단 확인에는 현재 게시본의 제목·개정을 표시하며, 중단해도 초안과 기록을 보존한다.

검색·상태·페이지와 선택 문서는 URL의 `q`, `status`, `page`, `id`에 보존한다. `mode=edit`는 편집, `revision=draft|published`는 읽을 개정이다. 기존 `?new=1`은 신규 초안 편집을 연다. 제목 입력과 상태 선택은 검색 버튼 또는 Enter로 함께 적용하며 첫 페이지로 이동한다. 검색 대상은 기존 서버 계약대로 **초안 제목**이다. 입력 중 조건과 적용 조건을 구분하고 결과 위에 적용 조건을 표시한다. 초기화는 입력·적용 조건을 함께 지우고 뒤로/앞으로 이동 시 입력도 URL과 동기화한다. 페이지 이동은 적용된 조건을 사용하고 범위를 벗어난 페이지는 보정한다. 결과 수는 상단에, 페이지 이동은 하단에 두며 한 페이지 이하면 이동 버튼을 생략한다. 목록 복귀 시 선택 행 포커스와 가능한 스크롤 위치를 복원한다.

제목·본문은 필수이며 라벨과 입력 속성으로 이를 제공한다. 입력 오류는 폼 상단 요약에서 필드로 이동할 수 있으며 추가 정보 오류는 접힌 영역을 펼친다. 미저장 취소·이탈은 확인한다. 409 충돌에서는 내 입력과 서버 최신 초안을 별도로 보존·표시한다. 최신본 조회 실패 시 ‘서버 최신본 다시 확인’으로 조회만 재시도하며 입력과 쓰기 멱등 키는 유지한다. ‘내 입력 복사’는 조회 성공 여부와 무관하게 제공한다. ‘내 입력 복사’로 보관한 뒤, 확인을 거쳐 ‘최신 초안 불러오기’를 선택한다. 통신 실패는 같은 멱등 키로 수동 재시도한다. 문서 작성은 관리 페이지의 새 문서 초안에서 시작한다.

## 저장과 상태

서비스 문서는 `var/documents.sqlite3`에 저장한다. `SANAEBI_DOCUMENT_DB`로 다른 경로를 지정할 수 있다. DB·WAL·SHM·백업은 Git에 넣지 않는다. 기존 `app/documents.jsonl`과 `data/company-knowledge/documents.jsonl`은 수정하지 않는다.

- 초안: 저장되었지만 답변 대상은 아니다.
- 게시: 지정한 개정본을 답변 대상으로 선택한다. 다음 검색 질문부터 적용한다.
- 적용 대기: 게시본의 시행일이 서울 기준 미래 날짜다.
- 수정 초안: 게시 후 편집한 내용은 새 개정본이며 재게시 전에는 기존 게시본이 유지된다.
- 사용 중단: 문서 제공 대상에서 제외하되 원문과 변경 기록은 보존한다. 영구 삭제는 제공하지 않는다.

이미 유효한 게시본이 있을 때 미래 시행일 개정본으로 교체하는 예약 기능은 제공하지 않는다. 해당 날짜에 수동 게시한다. 원문은 공백·개행까지 보존하며 메타데이터만 바꿔도 새 개정본을 만든다. 제목·본문이 같은 신규 문서는 중복 오류로 안내한다.

## API

웹은 아래 경로 앞에 `/api`를 붙인다. 개발 Next와 nginx가 FastAPI로 중계하면서 접두사를 제거한다.

| 경로 | 역할 |
|---|---|
| GET /documents/capabilities | local-demo·answer_integration="connected" (문서 연결 상태이며 품질·인증 보장은 아님) |
| GET /documents | 제목 검색·상태 필터·페이지 목록, 본문 제외 |
| GET /documents/maintenance-preview?action=clear\|restore | 전체 건수·복원 건수·상태 확인값 |
| POST /documents/maintenance | 전체 삭제 또는 기본 복원 |
| GET /documents/{id} | 초안·게시본 상세 |
| POST /documents | 초안 생성 |
| PATCH /documents/{id} | 새 초안 개정 |
| POST /documents/{id}/publish | 지정 초안 게시 |
| POST /documents/{id}/withdraw | 사용 중단 |

새 쓰기 API에는 UUID `Idempotency-Key`가 필요하다. 수정·게시·중단은 `expected_version`, 게시는 `revision_id`도 받는다. 같은 키로 같은 요청을 다시 보내면 기존 결과를 반환한다(24시간). 다른 요청에 같은 키를 쓰거나 다른 탭에서 먼저 수정했으면 409다. 자동 재전송하지 않으며 통신 실패 시 같은 요청의 키를 유지해 수동 재시도한다.

필수 제목은 최대200자, 본문은 최대50,000자다. 출처 이름·담당 부서·출처 URL·시행일을 추가할 수 있다. URL은 원본 위치 표시용이며 서버가 가져오지 않는다. JSON 요청 본문은 최대512KiB다. 신규 오류는 `{ok:false,error:{code,message,details?}}`이며 기존 질문/레거시 API의 응답 형식과 다르다. 모든 문서 API 응답은 no-store다.

`POST /regist-docs`는 기존 `{doc}` 입력과 성공 AnswerResponse를 유지하며 같은 SQLite에 초안을 저장한다. 제목은 본문 첫 유효 줄의 앞 200자다. 본문 50,000자·요청 512KiB 제한, 동일 제목·본문 중복 409가 적용된다. 레거시 등록은 자동 게시하지 않는다. 기존 JSONL 파일은 자동 이관하지 않으며 별도 레거시 이관 도구로 보존·이관한다.

## 데이터 공급과 답변

`DocumentContextProvider`는 SQLite에서 유효한 게시 개정본과 출처 메타데이터를 한 읽기 트랜잭션으로 확보한다. 초안·중단·미래 시행본은 제외한다. 한 검색 질문은 하나의 고정 snapshot을 사용하고 두 모델 비교도 같은 문서를 사용한다. LLM 호출 전에 트랜잭션을 닫는다. 게시본이 0건이면 모델 호출 없이 자료 없음 안내를 반환한다. DB 누락·손상·잠금 오류는 503이며 JSONL로 대체하거나 빈 목록으로 숨기지 않는다.

원본 문서는 이관 순서, 새 문서는 생성 시각·UUID 순서로 제공한다. 원문은 그대로 저장하고 생성 프롬프트에도 ID·개정·제목·본문·순서를 보존한다. 문서 전체 입력 방식은 유지하며 모델 문맥 한도·답변 품질은 별도 검증한다. `/assistant`도 `{ok,text,reason}`를 반환한다. 모델 호출 여부와 최종 생성 판정은 opt-in trace에서 확인한다. provider별 비교 결과는 과거 독립 실행기 계약이다.

SQLite schema v3는 문서 버전 하한을 관리하는 단일 행을 추가하며 기존 v1·v2 DB는 초기화 시 데이터를 보존해 마이그레이션한다. v2에서 도입한 기존 문서·개정·이벤트·멱등성을 유지하고 원본 이관 추적과 개정 메타데이터를 추가한다. 원본 ID·버전·출처 ID·정책 결정 ID·분류·검수 상태를 보존한다. 관리 UUID와 원본 ID는 다르다. 수정 개정은 출처 정보를 계승하되 `review_status=unreviewed`가 된다. 게시를 사람 검수 승인으로 해석하지 않는다. 상세 화면의 출처 정보는 읽기 전용이다.

기본 경로는 `SANAEBI_DOCUMENT_DB`로 통일한다. `IEUM_WORKS_PATH`는 런타임에서 사용하지 않고 경고한다. 명시적 평가 `--documents`는 고정 JSONL을 계속 읽으며 라이브 DB와 자동 병합하지 않는다.

## 회사 지식 이관·내보내기

### 새 환경의 DB 최초 구성

[의존성 설치](../README.md#로컬-개발-시작)를 마친 뒤 저장소 루트에서 **검증 → 이관·게시 → 게시 문서 확인 → 서버 실행** 순서로 진행한다. DB는 Git에 없지만 기본 원본 `data/company-knowledge/documents.jsonl`과 이관 스크립트는 포함되어 있다. 서버 시작은 빈 DB 구조를 준비할 뿐 기본 문서를 자동으로 채우지 않는다.

기본 DB는 `var/documents.sqlite3`다. 다른 경로를 사용하려면 아래처럼 지정하고, 이후 이관·확인·서버 실행에 같은 환경변수를 전달한다. 다른 터미널에서도 같은 값을 설정한다. 상대 경로는 실행 디렉터리 기준이므로 사용자 지정 경로는 절대 경로를 권장한다.

```bash
# 기본 경로를 사용할 때는 생략한다. 실제 사용할 경로로 바꾼다.
export SANAEBI_DOCUMENT_DB=/absolute/path/to/documents.sqlite3
```

기존 DB에 이관할 때는 먼저 서비스 쓰기를 중지한다. 아래 두 명령을 차례대로 실행한다. 기본 dry-run은 실제 DB를 생성·수정하지 않는다. 기존 DB는 메모리에 복제해 schema·중복·길이를 검사한다.

```bash
uv run --locked python scripts/import_company_knowledge.py --source data/company-knowledge/documents.jsonl
uv run --locked python scripts/import_company_knowledge.py --source data/company-knowledge/documents.jsonl --apply --publish-imported
```

게시 문서가 준비됐는지 확인한 뒤 서버를 시작한다. 진단 명령은 문서 수와 snapshot 식별값을 출력하며 모델을 호출하지 않는다. 새 DB에서는 원본의 게시 가능한 문서가 반영됐는지 확인한다.

```bash
uv run --locked python -m scripts.inspect_document_context
npm run dev
```

브라우저에서 http://127.0.0.1:3000/admin/documents 로 문서를 확인하고 http://127.0.0.1:3000/chat 에서 질문한다. 실제 답변에는 [분류 모델·생성 제공자 준비](../app/README.md#실행-준비와-api-확인)도 필요하다.

원본 이관은 기존 DB에서 편집한 최신 내용을 복원하지 않는다. 최신 편집본을 옮기려면 별도 DB 백업·복원이 필요하다. 시연용 reset 명령은 최초 구성에 사용하지 않는다.

### 재실행과 내보내기

`--apply`만 쓰면 초안으로 이관한다. `--publish-imported`는 새로 이관한 자료만 게시하며 과거 사용 상태를 이어가기 위한 옵션이다. 재실행은 같은 원본 행을 건너뛰고 원본 ID의 내용이 달라지면 중단한다. 수정·중단된 기존 문서를 재게시하거나 덮어쓰지 않는다. 전체 이관은 한 트랜잭션으로 처리한다. 원본과 DB 백업·hash·매핑 manifest는 DB 옆 `backups/knowledge-*/`에 남긴다. 실제 이관 전 서비스 쓰기를 중지한다.

```bash
uv run --locked python scripts/export_company_knowledge.py --output tmp/evaluation-documents.jsonl
```

내보내기는 현재 게시 snapshot과 `.manifest.json`을 함께 만들며 기존 파일은 덮어쓰지 않는다. 평가에는 이 파일과 대응하는 평가 세트를 명시한다. 원본 JSONL은 새 로컬 환경의 최초 이관 자료로 유지하며 DB 편집 결과로 자동 갱신하지 않는다. DB 자체는 Git에 넣지 않는다.

## 실행·보존

FastAPI와 Next를 모두 loopback에 실행한다. nginx는 [기존 실행 안내](../deployment/local-nginx.md)를 따른다.

```bash
npm run dev
```

DB가 다른 버전이거나 저장 불가능하면 오류를 확인하고 무조건 삭제·재생성하지 않는다. SQLite 실행 중 백업은 SQLite backup API를 사용한다. 단일 DB 파일을 실행 중에 복사하면 WAL의 최신 변경을 놓칠 수 있다.

레거시 이관 도구는 기본 dry-run으로 읽기·검증만 한다. `--apply`를 명시했을 때만 백업 후 초안으로 복사한다. 안정적인 source ID·행 번호·행 해시로 반복 이관을 추적하고, 기존 행 내용이 바뀌면 중단한다. 추가 행만 있는 재이관은 이미 복사한 행을 건너뛴다. 원본 파일을 삭제하거나 잘라내지 않는다. 실제 명령 옵션은 `uv run --locked python scripts/import_registered_documents.py --help`로 확인한다.

미저장 입력은 브라우저 메모리에만 있다. 닫기·이동 시 확인하고 새로고침 시 유실될 수 있다. 채팅에는 문서 등록 버튼을 두지 않는다. 문서 관리로 같은 탭 이동 시 대화가 있거나 요청 중이면 기록 소실·요청 취소를 확인한다. 취소하면 이동하지 않으며 작성 중 질문은 기존 앱 메모리 보존 정책을 따른다.

공유 운영에는 서버 인증·문서 권한·감사 주체·CSRF 정책·레거시 쓰기 경로 보호가 추가로 필요하다. 메뉴 숨김이나 noindex는 권한 검사가 아니다. 실제 사내 자료·다중 사용자 운영은 이번 범위 밖이다.

## 현재 로컬 전환과 모델 제한

2026-10-14에 회사 지식 71건을 실제 로컬 DB에 게시 상태로 이관하고 원본 ID·본문·제목·순서·메타데이터와 정규화 프롬프트를 전수 대조했다. 게시가 사람 검수 승인을 뜻하지는 않는다. 새 clone에는 DB가 없으므로 위 명시적 이관을 수행해야 한다.

현재 로컬 `/ask`는 요구하는 분류 모델 파일이 없어 503이다. 분류기를 거치지 않는 독립 Ollama 호출에서는 같은 71건 snapshot의 입력이 66,652토큰으로 측정되어 현재 `num_ctx=40960`을 초과해 400으로 실패했다. 본문은 절단하지 않았고 모델 설정을 변경하지 않았다. 관리·공급 연결과 실제 답변 생성 성공을 구분해야 하며, 모델 준비·전체 문맥 처리 방식은 후속 결정이 필요하다. 상세 증거는 [전환 작업 기록](worklogs/2026-10-14-sqlite-documents.md)에 둔다. UI/UX 게시 전 재검증에서도 같은 분류 모델 부재와 문맥 한도 오류가 확인됐다. 화면·접근성 검사와 미검증 기기 조건은 [UI/UX 작업 기록](worklogs/2026-10-14-document-management-ux.md)을 따른다.

## 문서 전체 관리

목록 위에서 **새 문서 초안**과 함께 제공하는 **모든 문서 삭제**, **기본 문서 복원**은 검색·상태 필터와 관계없이 활성 DB의 전체 문서를 대상으로 한다. 공개 시연 기능으로 제공하며 별도 관리자 키를 요구하지 않는다. 기존 공개 시연 쓰기 제한·요청 크기 제한·문서 오류 형식·no-store를 동일하게 적용한다.

| 작업 | 확인 입력 | 작업 후 상태 | 새 백업 |
|---|---|---|---|
| 모든 문서 삭제 | 전체 삭제 | 문서·초안·게시본·개정·이관 기록이 없는 상태 | 만들지 않음 |
| 기본 문서 복원 | 기본 문서 복원 | 서버의 기본 JSONL 전체가 게시된 상태 | 실행 전에 생성 |

기본 자료는 서버가 정한 `data/company-knowledge/documents.jsonl`이다. 클라이언트는 파일 경로를 지정할 수 없다. 기본 자료·기존 백업·모델·생성 사용량·실험 자료를 삭제하지 않는다. **이 관리 API 자체는 임베딩을 호출·삭제·초기화하지 않는다.** RAG worker의 후속 색인 갱신은 별도이며 아래 [RAG 안내](#rag-색인과-자정-초기화)를 따른다. 전체 삭제는 기본 자료가 없어도 실행할 수 있다. 자정 예약은 유지하므로 다음 예약 실행에서 기본 문서가 다시 복원될 수 있다.

확인창은 현재 전체 건수와 작업 후 건수를 표시하며 취소에 먼저 포커스를 둔다. 확인 문구가 정확히 일치해야 실행된다. 처리 중에는 다른 쓰기·화면 이동·중복 실행·닫기를 막는다. 성공 시 검색·상태·페이지·선택을 초기화하고 목록과 처리 건수를 갱신한다. 실패 시 입력과 적용 조건을 유지한다.

미리보기 응답은 `action, total_count, restored_count, expected_state`다. 실행은 `action, expected_state`와 UUID `Idempotency-Key`를 받으며, 완료 응답은 `action, deleted_count, restored_count, completed_at`만 제공한다. 내부 경로·원문은 반환하지 않는다. 확인 이후 문서 또는 복원 자료가 바뀌면 409이며 다시 확인해야 한다. 응답 유실 시 자동 재실행하지 않고 **같은 요청으로 결과 확인**을 누른다. 같은 키의 완료 결과는 24시간 재전달하며 그 사이 새 문서가 생겨도 작업을 반복하지 않는다.

DB별 초기화 잠금과 SQLite 쓰기 트랜잭션을 CLI·예약 초기화와 공유한다. 복원 자료 검증·백업 실패는 문서 교체 전에 중단하고 교체 중 오류는 롤백한다. 완료 이후 백업 결과 기록만 실패한 경우에도 동일 키로 저장된 완료 결과를 확인할 수 있다. 문서를 비워도 버전 하한을 보존하므로 삭제→복원 후 과거 편집 요청이 다시 유효해지지 않는다. 일반 쓰기 키는 남은 유효기간 동안 무효화하고 전체 관리의 완료 키는 재확인을 위해 보존한다.

기존 DB 마이그레이션은 앱의 저장소 초기화에서 수행한다. CLI는 지원하지 않는 스키마를 임의 초기화하지 않으므로 구버전 DB는 새 서버 버전으로 마이그레이션한 뒤 dry-run을 수행한다. 이미 확보한 답변 snapshot은 유지하고 이후 질문부터 변경한 문서를 읽는다.

## 공용 시연 문서 자정 초기화

시연 전용 DB를 저장소의 `data/company-knowledge/documents.jsonl` 기준으로 매일 한국 시간 00:00에 복원하는 관리 명령을 제공한다. **예약 설정 파일을 설치·활성화해야 실행된다.** 서버 시작 시에는 문서를 초기화하지 않는다. 수동 실행은 아래 관리 명령 또는 목록의 문서 전체 관리 기능을 사용한다. 화면의 자정 안내는 이 예약 운영을 전제로 한다. 실제 서버 활성화 절차는 [배포 안내](../deployment/README.md#운영-확인과-복구)를 따른다.

```bash
uv run --locked python scripts/reset_demo_documents.py --database /absolute/demo/documents.sqlite3
uv run --locked python scripts/reset_demo_documents.py --database /absolute/demo/documents.sqlite3 --apply
```

기본 실행은 원본과 DB를 메모리에서 검증하는 dry-run이다. `--apply`에서만 변경한다. `--source` 기본은 저장소 원본 JSONL, `--database` 기본은 `SANAEBI_DOCUMENT_DB` 또는 기존 로컬 DB 경로다. **예약 서비스에는 전용 시연 DB의 절대 경로를 반드시 명시한다.** 없는 DB를 자동 생성하지 않는다. 최초 준비는 기존 이관 명령을 사용한다.

복원은 기준 자료 전체를 게시하고 추가 문서·수정 초안·중단 상태·기존 개정 및 이관 기록을 제거한다. 해당 기록은 초기화 전 DB 백업에 남는다. 원본 JSONL 파일은 변경하지 않는다. 배포 시 원본 자료가 변경되면 다음 초기화부터 새 자료가 적용되므로 배포 전에 dry-run으로 검증한다. 기준 문서의 관리 ID는 유지하고 `record_version`은 증가시킨다. 오래된 편집 요청은 409, 제거된 문서 조회는 404다. 이전 일반 쓰기 멱등 키도 남은 24시간 유효기간 동안 409로 거부하며 만료 시각을 연장하지 않는다. 충돌 시 입력을 보관한 뒤 최신 화면에서 새 요청으로 작성한다.

DB별 프로세스 잠금과 SQLite 쓰기 트랜잭션으로 초기화를 직렬화한다. 다른 쓰기는 잠금 해제까지 대기하며 기존 DB 대기 한도를 넘기면 실패할 수 있다. 읽기는 부분 복원 상태를 보지 않으며 SQLite journal 모드에 따라 잠시 대기할 수 있다. 이미 확보한 snapshot으로 생성 중인 답변은 초기화 전 문서를 계속 사용하고 이후 질문부터 복원 자료를 사용한다. 자정 이후의 신규 작성은 다음 초기화까지 유지된다.

백업은 DB 옆 `backups/demo-reset-<실행 ID>/`의 `database.sqlite3`, `source.jsonl`, `manifest.json`이다. SQLite backup API로 WAL 내용도 포함하고, 백업 실패·지원하지 않는 스키마·잘못된 자료·검증 실패에서는 복원 내용을 커밋하지 않는다. manifest에는 원본 해시, 시각, 건수, 백업 위치와 결과를 남긴다. 백업은 민감한 원문을 포함할 수 있으므로 전용 계정으로 보관하며 Git에 넣지 않는다. 자동 삭제하지 않으므로 운영자가 용량과 보존 기간을 관리한다. `.reset.lock` 파일은 정상 실행 뒤에도 남으며 파일 존재 자체는 실행 중이라는 뜻이 아니다. 잠금 파일을 수동 삭제하지 않는다.

명령은 실패 시 비정상 종료하고 문서 내용 없이 오류 종류만 출력한다. 백업 디렉터리 생성 전 실패는 표준 오류에서 확인한다. `prepared` manifest 또는 커밋 뒤 manifest 기록 실패는 실행 결과가 불확실한 상태이므로 **실제 DB를 확인한 뒤** 재실행한다. 오류 메시지 원문이나 문서 본문은 journal에 남기지 않는다.

### 백업 복구

먼저 타이머와 FastAPI 및 DB에 쓰는 도구를 중지하고, 현재 DB·WAL·SHM을 별도 보존한다. 사용할 백업의 manifest와 `PRAGMA integrity_check`를 확인한다. SQLite backup API로 백업을 대상 DB에 복원하고 문서 수·게시 snapshot을 검사한 뒤 서비스를 재시작한다. 실행 중 DB 파일 덮어쓰기나 WAL 파일 임의 삭제는 하지 않는다. 필요한 시연 내용을 복구했다면 예약 초기화를 다시 켤 시점을 결정한다.

```python
# 모든 DB 사용 프로세스를 중지한 상태에서, 실제 절대 경로로 바꿔 실행한다.
import sqlite3
from contextlib import closing

with closing(
    sqlite3.connect("file:/absolute/backup/database.sqlite3?mode=ro", uri=True)
) as source:
    assert source.execute("PRAGMA integrity_check").fetchone()[0] == "ok"
    with closing(sqlite3.connect("/absolute/demo/documents.sqlite3")) as target:
        source.backup(target)
        assert target.execute("PRAGMA integrity_check").fetchone()[0] == "ok"
        assert not target.execute("PRAGMA foreign_key_check").fetchall()
```

## 사용자 화면과 내부 안내의 경계

인증·권한 검증 미제공, 로컬 시연 구성, 모델 준비 조건, 게시본 공급 연결 여부와 내부 ID·해시·이관 정보는 내부 문서/API에서 관리한다. 게시가 사람 검수 승인을 뜻하지 않는다는 해석도 내부 관리 기준이다. 화면에는 실제 검수 상태와 출처, 저장/게시/중단 결과를 표시한다. 매일 자정 초기화, 미저장 입력 소실, 초안과 게시본의 차이는 사용자 행동에 영향을 주므로 안내를 유지한다. 오류가 발생하면 현재 작업의 실패와 복구 방법을 안내하며 구현 상태를 추측해 덧붙이지 않는다.

## RAG 색인과 자정 초기화

RAG는 원본 SQLite의 게시 snapshot을 기준으로 별도 파생 색인을 관리한다. 초안은 검색하지 않고 새 게시본 색인이 준비될 때까지 검색503이 가능하다. 자정 복원은 기본 벡터 묶음을 새 개정에 연결하며 모델을 다시 계산하지 않는다. 연결 실패 시 원본을 다시 초기화하지 않는 [복구 절차](rag-runtime.md#자정-초기화용-벡터)를 따른다. full 모드의 기존 reset과 예산 DB는 유지한다.

전체 삭제 후 새 질문은 빈 snapshot 안내로 종료하며 검색·생성·생성 예약을 하지 않는다. 파생 색인 파일이 남아 있어도 현재 게시 개정 필터로 삭제된 근거는 새 요청에 사용되지 않는다. 기본 복원은 새 revision을 만들므로 worker가 연결을 마칠 때까지 RAG 요청은503이며 생성 예약을 소비하지 않는다. 동일 입력은 기존 색인 또는 기본 벡터에서 재사용한다. API의 저장소 기본 원본과 자정 초기화의 host 원본이 다르면 바뀐 입력은 worker가 임베딩하며, 이 경우 API 복원 전체에 추론0회를 보장하지 않는다. 자정 기본 묶음 복원의 추론0회 계약과 구분한다. 이미 snapshot을 확보한 진행 요청은 그 snapshot으로 끝난다.
