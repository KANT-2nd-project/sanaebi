## 1. 실행 모드 계약

신규 서버 설정 제안: `SANAEBI_ROUTING_MODE=gate|shadow`. **미설정 기본값은 gate**이며 잘못된 값은 시작 시 명확히 거부한다. 앱 시작 때 한 번 읽어 app.state에 저장하고 요청별 환경변수 읽기나 사용자가 보내는 모드 전환은 허용하지 않는다.

| 경우 | gate (기존 비교 기준) | shadow (관찰 후보) |
|---|---|---|
| 정상 SEARCH | snapshot→생성 | snapshot→생성 |
| 정상 CLARIFY/UNSUPPORTED | 현재 고정 안내, 문서·생성 0회 | 라벨 기록 후 snapshot→생성 |
| 알려진 분류 로딩/추론 장애 | 기존 503, 문서·생성 0회 | 안전한 오류 유형만 기록, snapshot→생성 |
| 예상 밖 분류 코드 오류·허용 밖 라벨 | 기존 500 | 500; 모든 Exception을 삼키지 않음 |
| 빈 게시 snapshot | 자료 없음 안내, 생성 0회 | 동일 |
| 문서 장애 | 503 | 동일 |
| 생성 실패 | 502 | 동일 |
| 빈/잘못된 요청 | 기존 422 | 동일 |

shadow에서는 분류가 **의미 차단을 하지 않는다**. 초기 구현은 기존 동기 추론을 그대로 사용하므로 분류 지연·잠금 대기는 여전히 요청 지연에 포함된다. 비동기 background, thread timeout, 중복 생성, 큐는 이번에 도입하지 않는다. 분류기 장애 때 계속 처리하는 것은 관찰 모드의 명시적 계약이며 생성 API 오류를 성공으로 바꾸는 fallback이 아니다.

알려진 장애는 `ClassificationUnavailable`, `ClassificationInferenceError`만 별도로 처리한다. 순수 서비스에 HTTP 처리를 넣지 않고, 필요하면 예외 타입을 가벼운 공통 계약으로 옮겨 기존 import 경로를 재수출한다. 서비스가 predictor의 torch/transformers를 새로 직접 import하는 구조는 피한다. catch 범위는 분류 호출에만 한정한다.

## 2. 함수와 파일별 구현 순서

### 단계 A — 문서 기반 답변 공통 함수

`app/questions/service.py`에 작은 `answer_from_published_documents(question, *, read_documents, answer)` 함수(이름 제안)를 추출한다. snapshot은 요청당 한 번, 비어 있으면 현재 고정 문구, 아니면 동일 객체를 answer에 전달한다. DB 트랜잭션이 원격 호출 전에 끝나는 구조를 유지한다.

기존 `handle_classified_question`의 gate 동작이 이 함수를 사용하게 만들되 모든 라벨의 관찰 가능한 결과는 그대로 유지한다. 먼저 이 변경만 검증한다.

### 단계 B — 모드·정책 연결

- `app/settings.py`: 두 값 검증 로더. `app/fastapi_main.py`: lifespan에서 모드 저장. 기존 앱별 classifier/answerer와 종료 처리는 유지.
- `app/questions/service.py`: `handle_question`과 `handle_classified_question`에 명시적 모드 전달. 내부 기본값도 gate로 두어 과거 호출 테스트의 뜻을 보존한다. 분류 라벨은 강제로 SEARCH로 덮어쓰지 않는다.
- `app/dependencies.py`: `/ask`와 `/assistant`에 같은 앱 모드를 주입. 환경·DB·모델 객체 선택은 DI 책임.
- `app/questions/router.py`: 입력·응답은 그대로. 503 문서 설명은 모드별 차이를 명시한다.

### 단계 C — /assistant와 분류 API 호환

`/assistant`는 현재 `AssistantRequest(response, classification_label)`를 유지한다. `response.ok=false`이면 기존 실패 안내로 끝나고 두 모드 모두 문서·생성 0회다. 유효한 label은 gate에서 정책 분기, shadow에서 **클라이언트 제공 관찰값**으로만 기록한다. 재분류하지 않는다. label 누락·허용 밖 값은 기존 스키마 오류로 처리한다.

클라이언트가 준 라벨을 서버 모델의 예측으로 표시하지 않는다. `/ask`는 `label_source=model`, `/assistant`는 `label_source=client`로 구별한다. 입력 label은 인증·권한 판단으로 사용하지 않는다.

`/classify/koelectra-base`의 출력·오류는 변경하지 않는다. 분류 API 자체는 모델 실패 시 503을 유지한다. 분류 API→assistant를 조합하는 외부 클라이언트는 앞 단계 실패 시 shadow의 이점을 받지 못한다. 공식 웹 `/ask` 흐름과 이 호환 경로를 구별한다.

### 단계 D — 추적 정보

`app/diagnostics/trace.py`의 기존 기록을 깨뜨리지 않는 선택 필드를 추가한다.

- routing_mode, label_source, classification_status(ok/unavailable/inference_error/not_run), label 또는 null.
- classification_elapsed_seconds는 해당 단계 실제 경과 시간. 기존 요청 시작 기준 필드는 의미를 바꾸지 않는다.
- route_action(fixed_clarify/fixed_unsupported/document_answer/no_documents/upstream_failure)과 생성 시도 여부. document_answer가 생성 성공을 뜻하지 않도록 기존 최종 생성 상태도 유지한다.
- 모델 식별자, snapshot/프롬프트/설정 해시, generation 최종 상태, 사용량·실패 종류는 기존 안전한 기록과 연결한다.

기존 trace를 읽을 때 누락 필드는 unknown/None으로 둔다. 과거 모드를 추측해서 재분류하지 않는다. 기본 로그에 질문·문서·원응답·예외 문자열·키를 추가하지 않는다. 기존 opt-in 원문 trace는 별도 민감 원자료로 유지한다. 예측 라벨을 Luna 프롬프트에 넣지 않아 비교를 오염시키지 않는다.

### 단계 E — 비교 실행기

생성 단독 평가로는 차단된 질문이 누락되므로 질문 서비스/실제 HTTP 경로를 호출하는 별도 종단 실행기를 둔다(경로 제안 `scripts/evaluate_routing_policy.py`). `generation_evaluation.selection`의 후보 튜닝 로직으로 대체하지 않는다.

실행 방식은 **격리된 모드별 프로세스 안에서 기존 ASGI 앱을 TestClient로 호출**하는 것으로 고정한다. gate/shadow 각 프로세스는 임시 DB와 고정 snapshot provider를 사용한다. lifespan 진입 전에 임시 DB 환경을 설정하고 진입 뒤 평가용 의존성을 주입한다. 실제 서비스 DB 게시·중단·reset은 실행하지 않는다. 각 프로세스가 자신의 클라이언트를 종료하며 별도 앱 팩토리를 도입하지 않는다. 제어기는 문항별 A/B 순서를 고정 seed로 교차 배치하고 원격 생성은 동시에 실행하지 않는다.

관측은 실행 전용 `TRACE_DIR`을 명시적으로 켜고 기존 응답 trace 헤더와 원장의 slot ID를 연결한다. 기본 trace가 꺼져 있으면 record 함수가 no-op이므로 HTTP 응답만으로 라벨·토큰 수집이 가능하다고 가정하지 않는다. HTTP 본문과 프로덕션 응답 계약에 실험 필드를 추가하지 않는다. 원자료 trace는 요청·응답을 포함할 수 있으므로 로컬 비공개 폴더에 보존하고 게시용 안전한 요약을 따로 만든다. 요청이 끝났는데 trace가 없거나 연결이 불명확하면 측정 실패/uncertain으로 기록하고 실행을 멈추며 자동 재호출하지 않는다.

실제 생성 예약 지점은 평가에서 주입한 answerer wrapper다. wrapper가 공유 원장에 slot의 생성 시도를 원자적으로 예약·영속 저장한 뒤 실제 `GenerationAnswerer.answer`를 정확히 한 번 호출한다. 예약 실패 또는 상한 도달이면 실제 answerer를 호출하지 않는다. 호출 전에 프로세스가 종료되어도 예약을 임의 환급하지 않는 보수적 상한이다. gate 차단·빈 문서에는 wrapper가 실행되지 않아 생성 예약도 없다. 모드별 프로세스가 공유하는 원장에는 프로세스 간 잠금/트랜잭션과 slot 고유 제약을 둔다. 메모리 카운터만 사용하지 않는다. 시도 원장은 trace 저장의 성공 여부와 독립적이다.

실행 manifest에 코드 commit+dirty diff hash, 원본 모델/설정, 프롬프트 원문 hash, 문서·문항·루브릭 hash, 모드, 반복, seed를 저장한다. 각 문항은 라벨과 최종 응답·HTTP 상태·지연·토큰·예상 API 비용을 함께 기록한다. 저장 시 원문은 로컬 원자료, 게시본은 검토된 합성 문항·답변과 요약만 사용한다.

완료 응답은 실패 포함 재개 시 재호출하지 않는다. 시작 기록만 남은 요청은 uncertain으로 보존하여 자동 재실행하지 않는다. 설정·코드·자료가 달라지면 같은 run 재개를 거부한다. 출력 덮어쓰기는 금지한다. 비용 미확인 값을 0으로 확정하지 않는다.

우선 `tests/test_question_service.py`, `tests/test_api.py`, `tests/test_trace.py` 등 관련 테스트에 회귀를 추가한다. 사용자에게 구현을 안내할 때 단계 A부터 작은 변경→실행→검토 순서를 따른다. AI가 미리 TODO를 완성하지 않는다.

구현 후 전체 Python unittest(저장소 기존 명령 확인), `uv run --locked ruff check .`, `uv run --locked ruff format --check .` 수행. 무관한 기존 실패는 변경 전 재현 여부를 분리한다. 웹은 코드 변경이 없으면 전체 build 반복 대신 /ask의 정상·오류·취소 호환을 해당 범위로 확인하고, 웹 수정이 필요하면 기존 웹 검증 절차를 적용한다.

## 4. 종단 비교 설계와 기본값 전환 게이트

아래 숫자는 **이번 계획의 제안 기준**이다. 실제 실행 전 사용자가 비용·지연 수용 조건과 함께 확정하고 manifest에 고정한다. 이번에는 질문 작성·실호출을 하지 않는다.

- 신규 40문항: 근거 있는 업무 안내 16, 부분/자료 부족 8, 범위 밖 6, 순수 조회/실행 4, 대상·의도 모호 4, 안내+실행 혼합 2. 문서 추가/개정/중단 사례를 관련 유형 안에 포함한다. 모든 문항의 snapshot을 사전 고정한다.
- 기존 48문항은 mock 라우팅 회귀 및 해석 참고로 유지하며 신규40과 합산하지 않는다. 회사/비회사, 짧은/긴 표현, 생소한 제도 등을 균형 있게 구성한다.
- 양 경로 각 2회: 160개 요청 슬롯, 생성 시도는 최대160회. gate 미호출은 생성 호출로 세지 않는다. 별도 실모델 smoke·자동 재시도 없음. 두 API 호환은 mock으로 검증하고 품질 비교는 `/ask` 경로 기준이다.
- 호출 전에 공유 원장에 생성 시도를 원자적으로 예약한다. timeout/실패/uncertain도 시도 상한에 포함한다. 경과 시간·실제 사용량·가격 출처 시점을 기록하고 금액·시간 한도는 실행 전에 별도 확정한다. 과거 다른 실험의 무제한 예산 승인을 재사용하지 않는다.
- 질문마다 허용 행동·필수 주장·금지 주장·근거 위치를 고정한다. 모호 요청에 구체적 재질문과 안전한 일반 안내 둘 다 가능하면 모두 허용한다. 블라인드 AI 평가·경계 근거 재검토이며 사람 검수로 표현하지 않는다.

기본값 전환 권고 조건 제안:

1. 허구 개인 조회·처리 완료·권한/정책 생성·범위 밖 사실 답변 같은 중대한 오류 0건.
2. shadow에서 두 반복 모두 허용 행동·필수 안내를 만족한 문항 최소36/40. 정상 안내16+혼합2 중 최소17/18이 두 반복 모두 통과.
3. 업무 안내의 불필요한 거절/재질문이 gate보다 감소하고, gate가 두 번 통과한 문항에서 shadow가 새로 실패한 사례 0건. 불확실을 통과로 치지 않는다.
4. 형식·timeout·API 오류를 포함해 보고하며 shadow의 새 실패가 있으면 기본값 전환 보류. 비용·지연의 사전 수용 한도도 충족해야 한다.

이 조건이 엄격해서 미달해도 결과를 본 뒤 기준을 낮춰 통과로 바꾸지 않는다. 개선 여부와 기본값 승격을 구별하고 후속 정책 판단은 새 결정으로 기록한다. 40문항 합성 평가로 일반 운영 정확도를 주장하지 않는다.

## 5. 전환과 원복

비교 구현 단계에서는 기본 gate를 유지하고 명시적 shadow 실행만 허용한다. 품질·비용 검토 후 사용자가 기본 전환을 결정하면 별도 커밋으로 기본값·운영 문서·Notion을 함께 갱신한다. 배포나 실행 서버 재시작은 별도 작업이며 이번 계획 검수에 포함하지 않는다.

원복은 `SANAEBI_ROUTING_MODE=gate`로 설정하고 해당 서버 프로세스를 재시작한다. 코드·모델·데이터를 되돌리는 재학습은 필요하지 않게 설계한다. 개인정보·권한 관련 오류가 보이면 결과를 보존하고 원복한다. 장기적으로 분류 자체를 제거할지는 별도 결정이며 초기 비교에는 포함하지 않는다.

## 6. 기능별 작업 단위와 게시

1. 공통 문서 답변 함수 추출 + gate 회귀.
2. 모드·DI·두 API 정책 + 분류 장애 처리.
3. 안전한 trace와 과거 기록 호환.
4. 고정 평가 자료·원장·재개 가능한 종단 실행기.
5. 실제 비교 결과·채택/보류 판단·문서·Notion.

이번 게시에는 위 구현 커밋이 없다. 결정·계획·독립 검수·기여 기록만 커밋한다. 정식 서비스 설계에는 ‘채택 방향, 미구현’ 요약을 연결하고 라벨 v1 본문·기존 실험 점수는 유지한다.
