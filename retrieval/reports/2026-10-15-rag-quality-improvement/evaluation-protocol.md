# RAG 검색 품질 평가 절차

## 목적과 상태

이 문서는 제목 경계 임베딩 문맥, 인접 청크 확장, BM25·벡터 결합 검색을 한 번에 하나씩 비교하는 절차를 고정한다. 실제 생성 모델 호출 없이 검색 후보와 최종 전달 근거만 평가한다.

`cases.json`은 AI가 저장소의 합성 회사 문서를 읽고 작성했다. 독립 AI 검토와 지적 수정 후 모델 검색 실행 전에 동결했다. 독립 검토자가 질문의 자연스러움, 출처 문서, 각 필수 구간의 의미·위치를 확인했다. 독립 검토 완료 전에는 후보 결과를 만들지 않는다. 검토·수정이 끝나면 파일 SHA-256을 실험 기록에 남기고 이후 질문과 구간을 바꾸지 않는다. 사람의 검수를 받았다고 기록하지 않는다.

## 평가 자료와 범위

| 묶음 | 문항 수 | 사용 목적 |
|---|---:|---|
| 기존 회귀 문항 | 18 | 이전 검색 결과와 비교하고 기존 성공을 보존 |
| 새 개발 문항 | 20 | 단계별 설정 비교와 채택 판단 |
| 새 최종 확인 문항 | 20 | 개발 문항으로 고른 최종 후보를 한 번 확인 |
| 답변 불가 문항 | 10 | 근거가 없는 질문의 검색 결과를 별도 점검 |

새 40문항은 표현 바꾸기, 제목·절 경계, 표, 정확한 용어, 예외, 여러 조건을 포함한다. 모든 답변 가능 문항은 하나의 기준 문서 ID를 가진다. 복수 조건을 묻는 문항은 `required_spans`의 **모든 구간**이 필요하다. `holdout_20`은 최종 후보가 고정될 때까지 열람해 튜닝하지 않는다. 파일 안에 holdout 질문이 함께 들어 있으므로 이는 접근 제어가 아니라 평가 절차상의 사용 제한이다.

## 원문 구간과 호환성

각 `required_spans` 항목은 `text`, `start`, `end`를 가진다. 오프셋은 `data/company-knowledge/documents.jsonl`의 지정 문서 `document` 본문에 대한 Python Unicode 코드 포인트 기준이며, `[start, end)` 반열림 구간이다. 제목과 JSON 메타데이터는 오프셋 범위에 포함하지 않는다. 반드시 `document[start:end] == text`여야 한다. 원문 파일 SHA가 달라지면 오프셋과 qrel을 그대로 사용하지 말고, 변경 원인을 확인한 뒤 다시 검토한다.

근거 포함은 전달된 각 증거의 `document_id` 및 원문 시작·끝 구간으로 판정한다. 같은 기준 문서의 전달 구간들을 합쳐 각 필수 `[start, end)`를 완전히 덮어야 포함으로 센다. 다른 문서의 같은 문구, 부분만 포함된 구간, 잘린 최종 컨텍스트는 필수 구간을 충족하지 않는다. 문자열 이어 붙이기나 정규화로 청크 사이의 누락을 가려서는 안 된다.

기존 18문항은 `legacy_qrel_compatibility.answerable`의 원래 `question`, `document_id`, `evidence` 값을 그대로 보존한다. 과거 비교와의 호환 지표는 해당 `evidence` 문자열 기준으로 별도 산출한다. 새 오프셋 구간으로 과거 결과를 다시 쓰거나 변경하지 않는다.

## 지표

주 지표는 최종 전달 근거에서 필수 구간을 전부 찾은 **완전 포함 문항 수와 비율**이다. 각 설정에서 다음을 따로 기록한다.

- 후보 상위 10개와 검색 상위 5개 근거 각각의 필수 구간 재현율 및 문항 완전 포함률
- 문자 예산 적용 후 최종 전달 근거의 필수 구간 재현율 및 문항 완전 포함률
- 문항별 포함 여부, 기준 문서 ID, 누락된 span ID, 최종 전달 문자 수
- 검색 지연의 p50·p95와 평가에 사용한 CPU·메모리·모델 revision·chunk spec·검색 설정

완전 포함 문항은 해당 문항의 필수 구간을 모두 전달했을 때만 성공이다. 비율의 분모와 원시 건수를 항상 함께 표시한다. 답변 가능 문항의 top-k 적중률과 최종 전달 포함률은 서로 대체하지 않는다. 답변 불가 10문항은 기준 문서나 필수 구간이 없으므로 주 지표 분모에서 제외한다. 해당 문항의 검색 결과는 따로 기록할 수 있지만, 실제 생성·사람 검토 없이 거절 정확도나 답변 안전성을 주장하지 않는다.

## 단계별 비교와 채택 규칙

모든 단계는 같은 Tiny 모델 ID와 고정 revision, 동일한 원문 SHA, 동일 질문, 동일한 CPU 실행 조건을 사용한다. 단계마다 바꾸는 요인은 아래 하나로 제한하고, 개발 문항과 18개 회귀 문항 결과를 이전 **채택** 설정과 비교한다.

1. **기준선:** 기존 벡터 검색, 기존 chunk spec, 후보 10개와 현재 근거 선택·문자 예산.
2. **제목 경계 문맥:** 본문 360 토큰은 유지하고 임베딩 전용 앞·뒤 문맥을 최대 60 토큰(기본 앞 30·뒤 30) 붙인다. 입력은 접두사·제목·특수 토큰을 포함해 512 이하로 제한한다. 새 chunk spec과 별도 색인을 사용한다. 결과 근거 원문 범위는 늘리지 않는다.
3. **인접 근거 확장:** 직전까지 채택된 구성을 기준으로, 같은 문서·같은 개정의 앞·뒤 인접 청크를 각각 최대 하나 확장한다. 같은 상위 절을 우선하며 허용된 절 경계와 원래 설정의 근거 수·문자 한도를 기록한다.
4. **BM25·벡터 결합:** 직전까지 채택된 구성을 기준으로, 고정 Tiny tokenizer의 특수 토큰 제외 토큰으로 BM25(`k1=1.2`, `b=0.75`)를 계산한다. 벡터와 BM25 각각 상위 20개를 동일 가중치 RRF(`k=60`)로 합쳐 후보 10개를 정하고, 이후에는 기존 근거 선택·예산 규칙을 적용한다. 검색 방식 설정은 벡터 spec과 별도로 기록한다.

단계의 기본 채택 조건은 18개 회귀·개발20문항의 기존 성공을 모두 유지하면서 개발20문항의 최종 완전 포함 건수가 직전 채택 설정보다 증가하는 것이다. 조건을 충족하지 않으면 해당 변형을 채택하지 않고 직전 구성을 기준으로 다음 단계를 실험한다. 동률이나 기존 성공 문항의 회귀가 있으면 더 복잡한 변형은 채택하지 않는다. 기존 회귀 18문항에서 알려진 경비 지급일·노출 토큰 두 사례는 각각 결과를 따로 표시한다.

세 단계 개발 비교가 끝나면 채택 조건을 만족한 가장 단순한 구성을 최종 후보로 고정한다. 그 뒤 현재 기준선과 최종 후보를 `holdout_20`에서 각각 한 번만 실행해 같은 지표를 산출한다. holdout 결과를 보고 설정·질문·qrel을 조정하거나 두 번째 holdout 평가를 하지 않는다. 최종 후보가 기준선보다 나빠지면 운영 후보 채택을 보류하고, 결과와 미해결 한계를 기록한다. 비교 개선이 없어도 실험 자체는 보고하되 운영 품질 통과로 표현하지 않는다.

## 실행 기록과 해석 한계

실험 보고서에는 실행에 사용한 정확한 명령, 코드 commit, qrel SHA-256, source SHA-256, 모델 ID와 revision, chunk spec, 단계별 검색 설정, 최종 전달 예산, CPU 자원, 원시 결과 파일 위치를 남긴다. 이 프로토콜은 실행 명령을 새로 정의하지 않는다. 저장소의 실제 평가 진입점과 옵션을 확인한 뒤 실행한 명령을 그대로 기록한다.

검색 실험은 근거를 검색·전달하는 능력만 평가한다. 실제 답변의 정확성, 근거에 따른 생성, 무근거 답변 억제는 모의 생성기나 검색 지표로 확인할 수 없다. 이 qrel은 합성·AI 검토 문서에서 AI가 작성한 개발 자료이며, 실제 회사 지침의 정확성·사람의 승인·운영 성능을 입증하지 않는다. 최종 운영 판단 전에는 새 질문에 대한 사람 검수, 실제 LLM 품질 평가, 배포 환경 성능 확인이 별도로 필요하다.

동결 SHA-256: `d7b26c63df2fce658982770ec5c48c5dfd587447ce5d7ade4931e1ce866c4c3d`. 중첩된 작은 필수 구간은 상위 필수 구간으로 통합해 구간 지표의 중복 가중을 제거했다. legacy 문자열 기준은 별도 보존했다.
