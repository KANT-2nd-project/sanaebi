# 현재 RAG 최소 4문항 진단 — 2026-10-16

현재 게시 문서71개·KURE 상위20/질문 게이트·v5·GPT-6 Luna(xhigh/16384/180초/prompt_json)로 질문당1회 확인했다. 분류 보조 전달은 현재 설정 advisory를 유지했다. 프롬프트·서버·검색 설정은 변경하지 않았다.

문서 DB와 색인을 SQLite 읽기 전용 연결의 backup으로 프로젝트 내부 영구 경로에 복사하고, 복사본의 준비 상태와 snapshot fingerprint를 확인했다. 실제 TransformerClassifier → handle_question → RetrievalService.retrieve → GenerationAnswerer.answer_retrieved → 제공자/기존 파서 경로를 별도 프로세스에서 실행했다. HTTP·브라우저·운영 서버 연결 검사는 아니며 운영 DB 쓰기·서버 재시작은 하지 않았다.

## 가장 중요한 원인

사고 질문은 ieum-035의 ‘즉시 신고 경로’와 ieum-031의 ‘링크 오류와 오공유’는 검색됐다. 그러나 전체 snapshot에 존재하는 ieum-035의 **접수와 담당 인계(15분 목표·미응답 대체 인계)** 및 **초동 조치와 금지 사항(증거 임의 삭제 금지·외부 통지 권한)**은 실제 전달 문맥에서 빠졌다. 관련 문서 ID를 찾았더라도 필요한 절 전체가 전달된 것은 아니다. 이 근거 누락을 프롬프트만의 오류로 분류하지 않는다.

수신자에게 연락할지·삭제 요청을 어떻게 전달할지에 대한 세부 문안은 현재 자료에서 확인되지 않는다. 모델이 이를 발명하지 않은 것은 적절하다. 다만 원문에 있는 대외 통지 권한 경계도 검색에서 빠져 답변이 충분한 안내에 이르지 못했다.

도움 소개는 gate 최고 점수0.473418로 통과해 안내했다. 연차 질문은 분류기가 UNSUPPORTED로 예측했지만 advisory 경로라 차단되지 않았고 정상 안내했다. 세그먼트 트리는 검색 결과0건에서 질문 서비스의 고정 응답으로 종료되어 **v5 프롬프트를 아예 거치지 않았다.** 이 문구 개선은 프롬프트 튜닝만으로 해결되지 않는다.

## 다음 조치 권고 — 이번에는 미구현

2. 게이트 차단 안내의 문구·지원 범위 표현은 검색 결과 없음 처리 정책에서 별도로 검토한다. 검색 결과가 없다는 사실만으로 업무 질문을 범위 밖으로 단정하지 않는다.
3. 도움 소개 가독성은 별도 작은 문제로 남긴다. 이번에는 정상 근거가 빠진 사고 질문의 검색 개선이 먼저다.

## 실제 답변

### Q1: 너는 뭘 도와줄 수 있어?

이음웍스의 사내 업무 정보·규정·절차와 문서에 설명된 업무 도구 사용을 안내해 드릴 수 있습니다. 예를 들어 휴가·근태, 구매·정산, 계정·기기, 보안 사고, 고객 문의 관련 절차를 안내할 수 있습니다. 다만 신청·변경·취소·승인이나 개인별 상태 조회를 직접 수행할 수는 없습니다. 어떤 업무가 궁금하신가요?

### Q2: 우리 회사 연차 규정에 대해 알려줘

연차 사용은 다음 기준으로 신청하시면 됩니다.

- **예정된 연차:** 사용 시작일 기준 3영업일 전까지 이음 포털 **인사 > 휴가**에서 신청합니다. 사용할 날짜와 업무 공백을 메우는 데 필요한 인수인계 항목만 적으시면 됩니다.
- **갑작스러운 사정:** 미리 신청하기 어렵다면 가능한 경우 근무 시작 전에 팀장에게 Slack으로 알리고, 여건이 되는 가장 빠른 시점에 포털 신청을 보완합니다.
- **신청 후:** 포털에서 접수 상태를 확인합니다. 팀장은 접수 후 1영업일 안에 승인하거나 People팀 확인 필요 상태를 남깁니다. 업무 조정이 필요하면 조정할 날짜나 인수인계 항목을 안내합니다.
- **변경·취소:** 날짜가 바뀌면 기존 신청을 수정하고, 사용하지 않게 된 연차는 시작 전에 포털에서 취소합니다. 포털에서 수정·취소할 수 없거나 처리가 끝났다면 같은 신청 번호를 적어 People팀에 정정을 요청하며, 중복 신청은 만들지 않습니다.

이 안내만으로는 법령상 연차 부여 일수나 개인별 잔여 일수를 계산할 수 없습니다. 포털 표시와 잔여 일수가 다르거나 적용 기준이 불분명하면 People팀에 확인해 주세요. 회사의 신청 일정은 법령상 권리를 줄이거나 포기시키는 조건이 아닙니다.

### Q3: 고객 정보가 든 메일을 잘못 보냈을 때 개인정보 사고 신고와 수신자 대응 절차를 알려주세요.

고객 정보가 오발송되어 노출 가능성이 있으면 실제 피해가 확인되기 전이라도 보안 사고로 즉시 신고하세요. 업무시간과 관계없이 Slack의 #security-incident 또는 이음 포털의 보안 신고를 이용하고, 두 경로가 모두 작동하지 않을 때는 입사 시 받은 오프라인 비상연락카드를 따르세요. 인지 후 30분 이내 접수는 운영 목표이므로 30분을 기다리지 마세요.

추가 전송·처리를 멈추고, 가능하면 메일 회수를 시도한 뒤 실제 회수 여부를 확인하세요. 수신자가 이미 열람·복사·다운로드하지 않았다고 단정하지 말고, 수신자·파일·전송 시각·회수 시도 결과를 기록하세요. 신고에는 발견 시각, 대상 시스템, 자료 종류와 등급, 영향받았을 수 있는 사람·업무, 이미 한 조치, 연락 가능한 회사 계정을 적되 고객 원본 자료·비밀번호·인증 코드는 첨부하지 마세요.

수신자에게 연락할지, 삭제를 요청할지, 응답을 어떻게 확인할지에 대한 구체적인 절차는 현재 확인하기 어렵습니다. 보안·개인정보 담당자가 영향, 증거 보존 및 필요한 보호 조치를 조정합니다. 관련 내용은 「보안 사고 신고와 초동 대응」, 「업무 파일 공유와 외부 제공」, 「업무 이메일과 메신저 사용」을 참고하세요.
