# CPU 측정 방식

개발 PC는 Intel Core Ultra 9 275HX, WSL2 Linux 환경이다. 검색 측정 프로세스의 affinity를 CPU 2개(2, 3)로 제한한다. 품질 비교의 BGE 계산은 별도 CPU 2개(0, 1)에서 진행되므로 같은 코어를 경합하지 않는다. 메모리·호스트 자원은 공유한다. 이 결과는 실제 운영 2vCPU 검증이 아니다.

각 구성·동시성은 새 프로세스에서 모델을 로드하고 warmup 뒤 질문을 실행한다. cache는 모델 객체만 재사용하며 질문 벡터·재정렬 점수는 매번 새로 계산한다. 고정 48문항의 지정 라운드를 반복하고, 동시에 진행하는 요청 수만큼만 제출한다. 응답 지연은 제출 시각부터 완료 시각까지로 잠금 대기를 포함한다. cold load, warm 지연, 단계별 시간, 최대 RSS를 분리한다.

## 탈락 확정 시의 선택적 조기 종료

BGE처럼 느린 후보에는 `--early-reject`를 사용할 수 있다. 이는 **채택을 위한 측정 생략이 아니라 불합격이 수학적으로 확정됐을 때만 중단**하는 옵션이다.

계획한 48개 응답 시간 중 측정한 값은 그대로 두고 아직 측정하지 않은 값은 모두 0으로 놓아 같은 선형 보간 방식의 p95를 계산한다. 실제 지연은 음수가 아니므로 이 값은 전체 측정을 완료했을 때 p95의 하한이다. 하한이 이미 3,000ms를 넘으면 남은 요청이 아무리 빨라도 기준을 충족할 수 없다.

중단 시 실제 측정 수, 계획 수, 하한, 표본 분포와 `early_rejected=true`를 저장한다. 표본 p95를 전체 계획 p95로 표시하지 않으며, 부분 실행은 절대로 통과 처리하지 않는다. 동시 요청 1·2는 각각 별도 프로세스로 검사한다. 최종 채택 후보와 C는 전체 라운드의 p95/RSS를 보고한다.

이 방식은 개발 검색 품질 결과나 신규 확인 문항을 보고 바꾸는 검색 정책이 아니다. 검색 인자·품질 점수·미판정 처리에는 영향을 주지 않는다.

## 실제 측정 요약

| 구성 | 동시1 warm p95 | 동시2 warm p95 | 최대 RSS | 판정 |
|---|---:|---:|---:|---|
| C | 36.79ms | 70.55ms | 1,009.49MiB | 자원 기준 통과 |
| 인접 확장 top12 | 37.27ms | 70.33ms | 1,009.41MiB | 자원 기준 통과 |
| BGE top40→12 | 최소 22,508ms | 최소 35,364ms | 3,681.82MiB | 지연 기준 탈락 |

C와 인접 확장은 동시성마다 48문항×5회=240요청을 완료했다. BGE는 예정 48개 중 각각 3개·4개에서 조기 탈락 조건을 만족했다. 표의 BGE 수치는 완료 측정 p95가 아니라 미실행을 0ms로 가정해도 넘는 **고정 표본 p95 하한**이다. 동일한 필수 40쌍 재정렬 단계의 하한도 각각 22,486ms·35,327ms여서 최종5·8·12 모두 이번 CPU 조건에서 제외했다. top5·8을 따로 성능 실행한 것으로 표현하지 않는다.
