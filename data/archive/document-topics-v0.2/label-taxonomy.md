# 분류·라벨링 기준

- 버전: 2.0
- 기준일: 2026-10-13
- 적용 범위: 직원 300명 이상의 기업용 업무·협업 SaaS 개발·운영 기업 이음웍스를 가정하고, 흩어진 전사 공통 규정·절차를 찾아 구성원의 반복 문의를 줄이는 사내비 프로젝트
- 적용 데이터: 기존 문서 주제 CSV 600건. 문서 제목과 본문으로 아래 6개 업무 주제 중 하나를 고르는 단일 라벨 다중 클래스 과제다. 현재 서비스의 요청 처리 분류 기준은 [서비스 아키텍처](../../../docs/service-architecture.md)에서 별도로 다룬다.
- 팀 기획·진행 문서: [Notion 프로젝트 메인](https://app.notion.com/p/2bb05a3cdadc82bb813381e3fab45047), [Notion 분류 기준](https://app.notion.com/p/3f805a3cdadc813485e4d94773974acc)

이 문서는 초기 6개 문서 주제 라벨과 라벨링 기준을 정한다. 문서 분류 라벨은 프로젝트 목적에 맞춘 결정이며 업계 공통의 고정 분류 체계를 뜻하지 않는다. 정의서의 존재만으로 데이터 작성·모델 학습·API·서비스 구현 완료를 뜻하지 않으며, 실제 데이터 준비 상태와 CSV 사용 방법은 [데이터 안내](README.md)에서 확인한다. 질문의 서비스 처리 분류와 답변 근거 원칙은 [서비스 아키텍처](../../../docs/service-architecture.md)를 따른다.

## 라벨링 단위와 공통 원칙

1. 한 문서의 제목과 본문을 함께 읽고, 작성 부서나 파일 형식이 아니라 실제 내용으로 판단한다.
2. 문서의 대표 목적이 되는 안내·규칙·절차에 라벨 하나를 붙인다. 부수적인 주제나 다른 부서의 단순 언급은 대표 주제를 바꾸지 않는다.
3. 여러 주제가 포함되면 문서가 주로 해결하는 업무와 독자에게 요구하는 핵심 행동을 기준으로 하나를 선택한다. 주제가 대등하면 검토 보류한다. 제목, 작성 부서, 단어 빈도나 본문 길이만으로 우선순위를 정하지 않는다. 단일 라벨을 강제하려고 문서를 임의로 쪼개지 않는다.
4. 내용이 부족하거나 분류 기준이 해결되지 않으면 추측해 라벨을 만들지 말고 **검토 보류**로 둔다. 현재 체계로 표현하기 어려운 정상 업무 문서는 **확장 후보**로 기록해 분류 체계를 검토한다.
5. 검토 보류·확장 후보 문서는 정답 확정 전 학습·평가용 정답 데이터에서 제외한다. 이러한 관리 상태는 업무 주제 라벨이 아니다.
6. `OTHER`, `기타`, `OOS` 토픽 라벨은 두지 않는다. 라벨이 하나도 없다는 이유만으로 문서나 질문을 범위 밖이라고 가정하지 않는다. 미분류 문서는 원인을 확인하고 보류 또는 taxonomy 검토 대상으로 처리한다.
7. 기존 4종 체계와 v1.0 다중 라벨 자료는 자동 변환하지 않는다. 배열의 첫 항목을 선택하지 않고 원문을 다시 검토해 v2.0의 대표 라벨을 정한다.

## 라벨

| 라벨 ID | 이름 | 대표 문서 |
|---|---|---|
| `HR` | 인사·근무·복지 | 연차 신청 규정 |
| `IT` | 계정·업무도구·IT 지원 | VPN 연결 절차 |
| `FINANCE_PROCUREMENT` | 비용·구매·정산 | 출장비 정산 규정 |
| `WORKPLACE` | 총무·시설·사무환경 | 방문객 출입 안내 |
| `SECURITY_LEGAL` | 보안·개인정보·법무 | 개인정보 외부 공유 기준 |
| `COMPANY` | 회사·조직 안내 | 조직도와 팀 역할 안내 |

### `HR` — 인사·근무·복지

- **포함:** 직원 휴가와 근태, 근무 제도·일정, 복지, 직원 급여, 입사·퇴사 절차와 인사 서류.
- **제외:** 계정 발급·접근과 업무 도구 설정은 `IT`; 직원 경비와 협력사 지급은 `FINANCE_PROCUREMENT`; 사원증의 사무실 출입 기능은 `WORKPLACE`.
- **긍정 예:** 연차 신청 규정, 근태 정정 절차, 복지 포인트 안내, 급여 명세서 확인법, 입사 서류 제출 안내.
- **경계 예:** 입사 서류 제출이 핵심이고 계정 신청 링크가 덧붙으면 `HR`이다. 계정 설정 자체가 핵심이면 `IT`, 출입증 이용이 핵심이면 `WORKPLACE`다. 세 목적이 대등하면 보류한다.

### `IT` — 계정·업무도구·IT 지원

- **포함:** 계정 생성·로그인·권한 요청, 업무용 소프트웨어와 협업 도구, VPN, 기술 지원, 업무 기기 설정·문제 해결.
- **제외:** 구매 승인과 지출·공급업체 정산은 `FINANCE_PROCUREMENT`; 정보 취급·외부 공유 규칙과 보안 사고 대응은 `SECURITY_LEGAL`; 사무실 출입은 `WORKPLACE`.
- **긍정 예:** SSO 로그인 안내, VPN 연결 절차, 협업 도구 사용법, 노트북 초기 설정과 기술 문의 절차.
- **경계 예:** 계정 권한을 신청하는 방법이 핵심이면 `IT`; 정보 접근 대상과 통제 원칙을 정하는 것이 핵심이면 `SECURITY_LEGAL`이다. 새 노트북 구매 승인은 `FINANCE_PROCUREMENT`이다.

### `FINANCE_PROCUREMENT` — 비용·구매·정산

- **포함:** 직원 경비, 출장비 정산, 법인카드, 구매 요청·승인, 세금계산서와 청구서, 협력사 대금 지급.
- **제외:** 직원 급여·복지와 직원 자격 요건은 `HR`; 기기 설정과 장애 해결은 `IT`.
- **긍정 예:** 영수증 첨부와 경비 청구 절차, 출장비 한도, 법인카드 사용·정산, 구매 승인 흐름, 협력사 청구서 처리.
- **경계 예:** 출장 경비의 신청·정산 규칙은 `FINANCE_PROCUREMENT`; 출장 중 근무 일정이나 휴가 제도는 `HR`이다. 공급업체 계좌 변경과 대금 지급 절차가 핵심이면 `FINANCE_PROCUREMENT`, 금융정보 보호와 보안 통제가 핵심이면 `SECURITY_LEGAL`이다. 두 목적이 대등하면 보류한다.

### `WORKPLACE` — 총무·시설·사무환경

- **포함:** 사무실·물리 공간 출입, 좌석, 회의실, 주차, 사무용품, 우편물, 시설 이용과 문의.
- **제외:** 계정 로그인이나 기기의 기술 설정은 `IT`; 구매 예산과 승인 절차는 `FINANCE_PROCUREMENT`; 근태와 근무 제도는 `HR`.
- **긍정 예:** 사원증으로 사무실에 출입하는 방법, 좌석 예약, 회의실 이용, 주차 신청, 우편물 수령과 사무용품 비치 안내.
- **경계 예:** 사원증 분실 시 사무실 출입 조치는 `WORKPLACE`; 계정 잠금 해제는 `IT`; 문서의 핵심이 출입증 분실에 따른 보안 사고 신고·대응이면 `SECURITY_LEGAL`이다.

### `SECURITY_LEGAL` — 보안·개인정보·법무

- **포함:** 정보 취급·보관·외부 공유, 개인정보 보호, 보안 통제와 사고 대응, 계약 검토, 윤리·준법 절차.
- **제외:** 모든 회사 정책을 포괄하는 라벨이 아니다. 계정 사용법은 `IT`; 일반 사무실 운영은 `WORKPLACE`; 내용상 보안·법무 주제가 없는 인사 규칙은 `HR`이다.
- **긍정 예:** 개인정보 처리와 파기, 외부 파일 공유 기준, 보안 사고 신고, 계약서 검토 흐름, 이해 상충·윤리 신고 안내.
- **경계 예:** MFA 등록 방법이 핵심이면 `IT`; MFA 의무와 보안 통제 원칙이 핵심이면 `SECURITY_LEGAL`이다. 계약 검토는 `SECURITY_LEGAL`, 구매 승인과 지급은 `FINANCE_PROCUREMENT`로 대표 목적을 구분한다.

### `COMPANY` — 회사·조직 안내

- **포함:** 회사 소개, 조직과 역할, 공식 소통 채널 등 회사의 구조와 기본 안내.
- **제외:** 다른 라벨을 대신하는 포괄 라벨이 아니다. 주제별 정책·절차는 해당 라벨을 붙이고, 회사 이름이 문서에 나온다는 이유만으로는 붙이지 않는다.
- **긍정 예:** 회사의 사업과 조직 구성 소개, 조직도와 팀 역할, 공식 공지·문의 채널 안내.
- **경계 예:** 조직도와 함께 각 팀의 대표 문의 채널을 안내하면 `COMPANY`; 휴가 신청 담당자만 적힌 휴가 규정은 `HR`이다. 사무실 좌석 문의 채널은 `WORKPLACE`이다.

## 경계 사례와 별도 상태

### 입사 안내 문서

입사 서류 제출이 중심이고 계정 신청 링크만 덧붙인 문서는 `HR`이다. 인사 서류·계정 설정·출입 절차를 대등하게 설명하는 종합 입사 안내는 보류한다. 작성 주체가 인사팀이라는 이유로 `HR`을 선택하지 않으며, 보류 문서는 최종 학습·평가 데이터에서 제외한다.

### 협력사 청구서

청구서 접수와 지급 절차가 대표 목적이면 `FINANCE_PROCUREMENT`다. 개인정보·계좌 정보 보호 규칙이 대표 목적인 문서는 `SECURITY_LEGAL`이다. 계좌번호나 개인정보라는 단어만으로 대표 주제를 바꾸지 않는다.

### 문서 주제 라벨과 질문 처리 분류 구분

여섯 라벨은 문서의 대표 업무 주제이며 사용자 질문의 처리 경로를 뜻하지 않는다. 이전 서비스 설명의 `IN_SCOPE` 검색·`OUT_OF_SCOPE` 안내·`UNCLEAR` 되묻기 표현과 중간 초안의 `ANSWER_FROM_DOCS`는 과거 표현이다. 현재 질문 처리 라벨은 `SEARCH_KNOWLEDGE`, `CLARIFY`, `UNSUPPORTED`이며, [서비스 아키텍처](../../../docs/service-architecture.md)에 경계 사례와 처리 흐름을 기록한다.

문서 기반 답변 경로를 선택해도 근거가 확보된 것은 아니다. 등록 자료에 답이 없거나 자료 간 충돌이 있으면 답변 단계에서 이를 구분해 알린다. 이 문서의 여섯 라벨 정의와 v2.0 버전은 그대로 유지한다.

## 확장 후보와 버전 관리

개발·서비스 운영 지식은 후속 업무 영역 후보로 둔다. 업무 실행과 개인의 실시간 정보 조회는 후속 기능 확장으로 구분한다. 기능이 늘어난다고 바로 문서 주제 라벨을 추가하지 않으며, 실제 문서와 사용 사례에 따라 주제 체계 또는 질문 처리 경로를 검토한다.

라벨 ID는 안정적으로 유지한다. 새 라벨 추가, 분할, 병합, 의미 변경은 버전을 올리고 변경 이유와 영향받는 기존 데이터를 기록한 뒤 재검토·재라벨링한다. 표시 이름이나 예시를 다듬더라도 의미가 달라졌다면 의미 변경으로 취급한다.

v2.0은 다중 라벨에서 단일 대표 주제로 바뀐 호환되지 않는 변경이다. 라벨 ID는 유지하되 기존 정답은 재검수한다. Notion의 중간 단일 라벨 기준 v1.1도 v2.0으로 통일한다. 데이터셋 v0.2는 600건의 내용과 라벨을 유지하면서 CSV의 `split` 열을 제거한 형식 변경이며, 라벨 기준은 v2.0으로 유지한다. 당시 시드 `20261013`을 고정한 분할은 문서화된 계획으로 남아 있고, 현재 구현은 `classification/legacy/document_split.py`에서 기본 시드 `42`를 사용한다. 데이터 구성, 계획과 구현의 구분, 검증 범위는 [데이터 안내](README.md)에서 관리한다. 새 문서 분류 모델 종류, 신뢰도 처리와 실제 API 연결 계약은 후속 실험에서 결정한다.

## 향후 평가 원칙

단일 라벨 다중 클래스 평가는 Accuracy, Macro-F1, 클래스별 Precision·Recall·F1, 혼동행렬을 함께 보고 오분류 사례를 검토한다. 모든 클래스에 대해 계산한 Micro-F1은 이 설정에서 Accuracy와 같으므로 별도 핵심 지표로 중복 보고하지 않는다. 원문, 복사본, 개정본, 청크처럼 같은 출처 문서 계열에 속한 데이터는 학습·검증·테스트 중 한 분할에만 둬 데이터 누수를 막는다. 신뢰도 기준이나 모델 선택은 검증 세트에서 하고, 최종 테스트 결과는 선택을 마친 뒤 평가한다.

이 문서의 사례는 라벨링 기준 예시다. 데이터 준비 상태는 데이터 안내와 실제 CSV 검증 결과를 함께 확인한다. AI 검수를 사람의 정답 검수로 표현하지 않으며, 데이터 준비는 모델 학습이나 서비스 구현 완료를 뜻하지 않는다.
