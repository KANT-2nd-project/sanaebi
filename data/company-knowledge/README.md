# 이음웍스 회사 정책 데이터

정책 52개·개발 평가 질문 208개를 수록한다. 확인한 사용 출처 12개와 회사 결정 51개를 연결했으며, 독립 AI 내용 검수 결과와 사람 승인 여부는 아래 기록에서 구분한다.

대한민국의 업무·협업 SaaS 회사 **이음웍스**를 배경으로 작성한 한국어 가상 회사 핸드북이다. 공개 자료의 원칙과 절차를 참고하되 회사 고유의 운영 선택을 별도로 정했다. 실제 회사의 사규, 직원 기록 또는 법률 검토를 마친 취업규칙이 아니다.

## 회사 설정

시연 설정은 직원 320명이다. 실시간 인원 조회나 특정 직원의 정보가 아니다. 구성원·팀장·People팀·재무팀·IT운영팀·보안·개인정보 담당자·총무 담당자가 역할을 나눈다. 협업은 Slack, 문서는 Google Workspace, 개발은 GitHub, 신청·승인은 가상의 이음 포털을 사용한다. 주 5일·주 40시간 기본 근무와 사전 승인형 재택근무를 기준으로 한다.

본문의 시스템 소유자는 IT운영팀 안에서 해당 시스템을 맡는 담당자이며, 자료 소유자는 팀장이 지정한 구성원이다. 별도 부서를 뜻하지 않는다. 총무 담당자는 시설·방문·자산·출입 절차를 맡는다. 팀장이나 기술 담당자의 승인이 보안·개인정보 검토를 대체하지 않는다.

본문의 승인 역할·신청 기한·금액·복지는 이음웍스의 가상 결정이다. 다른 회사의 정책을 이음웍스가 실제 채택했다는 사실로 주장하지 않는다. 법적 권리를 팀장 승인이나 사내 기한으로 제한하지 않으며 보안·개인정보 예외는 해당 담당자의 검토 없이 허용하지 않는다.

## 제작과 검수

연차·근무시간·재택·온보딩·퇴사·출장·정산·권한·MFA·사고·공유·AI 사용의 12개 파일럿을 작성·수정·독립 재검수한 후 52개 주제로 확장했다. 세부 제작·검수 근거는 manifest와 검수 기록을 따른다. 작성자와 별도의 AI 검수자가 52개 본문·208개 평가·미기재 질문의 전체 정책 대조를 수행했고, 지적 사항을 수정한 뒤 재검수했다. [최종 검수 기록](reviews/full-round-2.json)에 범위와 한계를 남겼다. 사람의 정책·법률 승인 및 실제 직원 질문에 대한 품질 검증은 수행하지 않았다.

미기재 정보 질문도 회사 정책 안내를 요청하면 `SEARCH_KNOWLEDGE`다. 안내와 실행이 섞인 질문에는 안내 가능한 부분만 답하고 실행할 수 없음을 밝혀야 한다. 208개는 답변 단계 개발용 세트이며 세 라벨의 균형 분류 평가 세트가 아니다. 전체 분류 학습 데이터와 과거 실험 결과는 수정하지 않는다.

## 개정 절차

1. 기존 주제의 `document_id`는 유지하고 본문 변경 시 `version`을 갱신한다. 출처의 실제 구역·판본·이용조건을 다시 확인하고, 회사 결정의 적용 문서와 본문의 결정 참조를 함께 맞춘다.
2. 해당 문서의 네 평가 질문·필수 사실·근거 절·금지 주장을 갱신한다. 다른 문서에 새 정보가 생겨 미기재 질문의 답이 생기지 않았는지 전체 묶음과 대조한다.
3. 작성자와 별도로 검수하고 본문 SHA-256, 지적 사항과 수정 결과를 `document-review.csv`와 `reviews/`에 남긴다. 이전 검수 기록은 당시 해시와 함께 보존한다. AI 검수만으로 `human_approved`를 바꾸지 않는다.
4. 새 릴리스 manifest에 문서별 순서·버전·본문 해시와 산출물 파일 해시를 기록하고 아래 검증을 실행한다. 문서와 평가 질문은 같은 릴리스로 선택한다. 정책 내용의 기준은 JSONL이며 별도 생성 스크립트를 두 번째 원본으로 관리하지 않는다.

## 사용과 이전 자료

서버 의존성 조립과 독립 답변 실행기의 기본 읽기 경로는 이 폴더의 `documents.jsonl`이다. `IEUM_WORKS_PATH`로 별도 파일을 지정할 수 있다. 등록 API가 사용하는 `app/documents.jsonl`은 별개이며 자동으로 병합하지 않는다. 기본 읽기 경로 변경이 미완성 `/ask`의 구현 완료를 뜻하지 않는다.

[초기 더미와 개발 평가 보관본](../archive/company-knowledge-v0/README.md)은 당시 바이트·행 순서로 보존한다. 평가 실행기는 모든 문서에 ID가 없는 보관본만 행 번호를 사용하고, 새 자료에는 명시적 ID를 사용한다. ID를 섞거나 중복·빈 값으로 넣으면 실패한다. 과거 평가에는 보관 문서를 명시적으로 지정한다.

## 검증

```bash
uv run --locked python scripts/validate_company_knowledge.py
uv run --locked python -m answer_pipeline.cli run --models data/company-knowledge/evaluations/models.offline-check.json --run-dir tmp/company-knowledge-dry-run --dry-run
uv run --locked python -m unittest discover -s tests -v
uv run --locked ruff check .
uv run --locked ruff format --check .
```

형식·참조·해시 검사는 정책 의미나 법적 정확성을 보증하지 않는다. dry-run은 문서·평가 질문의 정합성만 검사하며 모델을 실행하지 않는다. 실제 모델의 tokenizer 기준 입력 한도와 답변 품질은 후속 확인 대상이다. 전체 문서가 길어져도 몰래 자르거나 입력 제한을 일괄 늘리지 않는다.

평가 CLI의 기본 질문 세트는 이 정책의 208개 질문이다. 다른 평가 파일을 지정하면 `--documents`로 같은 버전의 문서를 명시해야 한다. 위 모델 설정은 dry-run용으로 로컬 제공자만 나열했으며 `--dry-run`을 제거하면 실제 로컬 모델 호출을 시도한다.

질문 입력의 `MAX_INPUT_CHARS=4000`은 전체 문서의 토큰 한도가 아니다. 현재 실행기는 정책 전체를 문맥에 넣으며 전체 문맥의 모델별 토큰 사전 검사는 구현하지 않았다. 기본 Ollama 설정 `num_ctx=16384`에 새 자료가 들어간다고 보증하지 않는다. 실제 실행 전 tokenizer·출력 여유를 포함해 별도로 측정해야 한다.

이번 릴리스의 `load_document_context()` 결과는 45,301자·UTF-8 106,560바이트다. 이는 문서 문맥만의 크기이며 질문·공통 지침·출력 여유를 포함한 모델 토큰 수가 아니다.

미기재 52문항은 본문에서 추출할 정답 사실이 없으므로 `required_points`를 비워 둔다. dry-run의 해당 52개 경고는 A4 핵심 정보 포함 점검을 수행하지 않는다는 뜻이다. 자료 부족 고지·금지 주장·기대 행동은 별도 평가 근거를 따라 확인해야 하며 이 경고를 답변 품질 통과로 처리하지 않는다.
